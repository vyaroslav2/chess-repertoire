## Proposed Prisma Models

### The Cache Layer (Raw API Data)
These tables store raw API responses. They are completely independent of any specific repertoire or algorithm run.

#### `PositionCache`
Stores the isolated FEN.
- `fen` (Unique ID)
- `eco`
- `openingName`
- `wikiText`

#### `ExplorerCache` (Replaces your "Lichess" column)
Stores the aggregate responses from Lichess. (One `PositionCache` can have many `ExplorerCache` rows).
- `positionId` (links to PositionCache)
- `dbType` (Masters, Elite, Amateur)
- `san` (The candidate move)
- `games`, `whiteWins`, `draws`, `blackWins`

#### `EngineEvalCache` (Replaces your "chessdbEval/lichessEval" columns)
Stores the Cloud Eval / ChessDB evaluations. (One `PositionCache` can have many `EngineEvalCache` rows).
- `positionId` (links to PositionCache)
- `san` (The candidate move)
- `cp` (Centipawns)
- `mate`
- `rank` (1st choice, 2nd choice)
- `source` (lichess or chessdb - both can exist simultaneously)

==1. Is the following correct:==
==Imagine you are looking at the starting position (`fen: rnbqkbnr/...`).== 
==You want to evaluate the move `1. e4`.==
==You query the Lichess Cloud Eval API. It says +0.3.==
==You query the ChessDB API. It says +0.5.==

==Because `EngineEvalCache` is a separate table, you can insert **two separate rows** for the exact same position and move:==

| positionId (FEN) | san | cp | source |
| :--- | :--- | :--- | :--- |
| rnbqkbnr/... | e4 | 30 | lichess |
| rnbqkbnr/... | e4 | 50 | chessdb |

==They "exist simultaneously" in the database. When your algorithm runs, it can look at the cache, see both evaluations, and decide which one it trusts more (e.g., "ChessDB has a higher depth, I'll use that one"). This prevents you from having to create hardcoded columns like `chessdbEvalCp` and `lichessEvalCp` in your tables.==

### The Algorithm Layer (Repertoire State)
These tables represent your specific repertoire tree generated by the BFS algorithm. 

#### `RepertoireNode` (Matches your `Line` bucket)
- `fen` (Unique ID for this node in the tree)
- `pgn` (The exact move history to reach here)
- `cumulativeProb` (e.g. "1 in 500 games")
- `isAmateurTrap`, `isMasterThreat`

### ==2. The Transposition Problem (Crucial Fix)==
==**The Issue:** In `RepertoireNode`, you proposed `fen` as the Unique ID. This will break your algorithm when encountering transpositions. Two different move sequences (PGNs) can result in the exact same position (FEN).== 
==*Example:* `1. e4 e5 2. Nf3 Nc6` results in the same FEN as `1. Nf3 Nc6 2. e4 e5`. If FEN is the unique ID in the Repertoire tree, you cannot store both historical paths, meaning your `cumulativeProb` and `pgn` fields will collide.==

==**The Fix:**== 
* ==`PositionCache` **should** use FEN as the unique ID (because the evaluation and Lichess stats are identical regardless of how you reached the position).==
* ==`RepertoireNode` **must** use a UUID, auto-increment ID, or the full `pgn` as the Unique ID. It should contain `fen` merely as a Foreign Key pointing to `PositionCache`.==

==If a `RepertoireNode` is a Line, its Unique ID **cannot** be the FEN. Here is why:==
==Imagine you are building your repertoire and two different lines transpose into the exact same board position.== 
*   ==**Line A (PGN):** `1. e4 e5 2. Nf3 Nc6` -> Reaches Position X (FEN).==
*   ==**Line B (PGN):** `1. Nf3 Nc6 2. e4 e5` -> Reaches Position X (FEN).==

==Because the board looks exactly the same, the FEN for Line A and Line B is 100% identical.== 
==If your database table `RepertoireNode` uses `fen` as its Unique Primary Key, you can only store **one** of those lines. When the algorithm tries to save Line B, the database will say: *"Error: This FEN already exists!"* and it will overwrite Line A. This means you lose the `cumulativeProb` and the unique `pgn` history of Line A.==

==**The Solution:**==
*   ==**`PositionCache` table:** Primary Key is `fen`. (Because the raw stats and eval are the same no matter how you got there).==
*   ==**`RepertoireNode` table:** Primary Key is `pgn` (or a random UUID). It has a standard column called `fen` which is a **Foreign Key** pointing to the `PositionCache`.== 

#### `OpponentMove` (Matches your `OpponentMove` bucket)
The white threats included by the algorithm.
- `fromNodeId`, `toNodeId`
- `san`
- `prob` (e.g. 15% chance they play this)
- `trueProbability`

#### `OurResponse` (Matches your `Response` bucket)
The black move chosen by our algorithm.
- `fromNodeId`, `toNodeId`
- `san`
- `weightedCount` (The volume score used to pick it)
- `lichessCp` (The lichess eval at the time)
- `chessdbCp` (The chessdb eval at the time)
- `engineSource` (Which engine we ended up trusting)

### ==3. FEN Normalization (Pro-Tip for Caching)==
==When saving the `fen` in `PositionCache`, make sure you strip out the **half-move clock** and potentially the **full-move number** (the last two numbers in a FEN string).== 
*   ==*Why?* If you reach a position on move 5 vs move 6, the API stats for the moves are exactly the same, but the literal FEN string will be different, resulting in unnecessary API calls and database duplication.==




### ==4. Unifying the Edges (Architectural Suggestion)==
==Currently, we have two separate tables for edges: `OpponentMove` and `OurResponse`. Because a chess game strictly alternates, maintaining two separate edge tables will make querying the full repertoire tree via Prisma recursively very difficult.== 

==**Recommendation:** Combine them into a single `RepertoireEdge` table with a discriminator:==

```prisma
model RepertoireMove {
  id              String
  fromNodeId      String
  toNodeId        String
  san             String
  playerTurn      String  // "OPPONENT" or "RESPONSE"
  
  // Opponent specific fields (nullable if RESPONSE)
  prob            Float?
  trueProbability Float?
  isAmateurTrap   Boolean?
  isMasterThreat  Boolean?

  // Response specific fields (nullable if OPPONENT)
  weightedCount   Float?
  lichessCp       Float?
  chessdbCp       Float?
  engineSource    String?
}
```
==*Why this is better:* If you want to render the tree on the frontend, you can just query `RepertoireMove` recursively without having to do complex `UNION` joins between `OpponentMove` and `OurResponse`.==
