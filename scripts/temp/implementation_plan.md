# Database Architecture Redesign

Separating the raw API cache from the calculated algorithm state is a brilliant idea. Right now, if we tweak the algorithm (e.g., change the Bayesian constants) and want to regenerate the tree, deleting the database means we lose all the cached Lichess/ChessDB responses and get rate-limited again. 

By splitting the tables, we can query Lichess *once* per position, store the raw data forever, and run the BFS algorithm instantly across our local DB.

## Proposed Changes

We will restructure `schema.prisma` to cleanly separate the Cache layer from the Algorithm layer.

### The Cache Layer (Raw API Data)
These tables store raw API responses. They are completely independent of any specific repertoire or algorithm run.

#### `PositionCache`
Stores the isolated FEN and its static data.
- `fen` (Unique ID)
- `eco`
- `openingName`
- `wikiText`

#### `LichessExplorerCache` & `MastersExplorerCache`
Stores the aggregate responses from Lichess.
- `fen`
- `san` (The move) // ==Is it the last move in position?[^2]== 
- `games`, `whiteWins`, `draws`, `blackWins`
- (We will store the 3 tiers: Masters, Elite 2500+, Amateur 1600-2000)

#### `EngineEvalCache`
Stores the Cloud Eval ==Do you mean Lichess by Cloud Eval?==[^3] / ChessDB evaluations.
- `fen`
- `san`
- `cp` (Centipawns)
- `mate`
- `source` (lichess or chessdb) ==This design allows us to keep only one. Which is a problem. I want both.==[^4]

### The Algorithm Layer (Repertoire State)
These tables represent your specific repertoire tree generated by the BFS algorithm. If we change the math, we can wipe these tables and rebuild them in seconds using the Cache Layer.

#### `RepertoireNode` (replaces `Line`)
- `fen`
- `pgn` (The history path to get here)
- `cumulativeProb` (e.g. "1 in 500 games")
- `isAmateurTrap`, `isMasterThreat`

#### `OpponentMove` 
The white threats included by the algorithm.
- `fromNodeId`, `toNodeId`
- `san`
- `prob` (e.g. 15% chance they play this)

#### `OurResponse`
The black move chosen by our algorithm.
- `fromNodeId`, `toNodeId`
- `san`
- `weightedCount` (The math result used to pick it) ==Explain in more depth, what is it and why do we need it.==[^5]
- `engineCp` (The exact eval used to validate it) ==How about rank and source?==[^6]
