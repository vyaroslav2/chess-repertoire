# B3 — Forced-mate handling before the candidate loop

## What the code does

B3 starts after [[B2]] has gathered engine data.

The current code builds one `baselinePvs` list:

- use the main engine list if it has anything;
    
- otherwise use the separate ChessDB list;
    
- if both are empty, run local Stockfish shallow at **depth 18, MultiPV 15** and use that result as the baseline.
    

It then takes the first entry from that baseline.

If that top entry has:

- a mate field;
    
- and the mate value is negative, meaning a forced mate for Black under the current score convention,
    

B3 enters its special **"KILL MODE"**.

In KILL MODE, B3 ignores the human shortlist entirely.

It prints that a forced mate was detected and immediately runs local Stockfish again, this time:

- one move only;
    
- depth 24.
    

It takes that deep engine move, converts it to SAN, saves it in `EngineEvalCache` under source `"local_deep"`, and immediately returns it to A4 as the selected Black response.

B4's normal human-candidate loop is skipped completely.

If there is no forced mate in the top baseline entry, B3 does nothing special and execution continues into the ordinary candidate-selection code.

There are several details in the current flow:

- ChessDB cache rows carry `mate: null`, so a ChessDB baseline cannot trigger the mate check.
    
- If neither API supplies anything, B3 runs the shallow local engine before the candidate loop even though it does not yet know whether local analysis is needed.
    
- If that shallow local result reports mate, B3 then runs a second, deeper local search.
    
- The deep result can be a move that does not appear in the human shortlist at all.
    
- That move is returned immediately with source `"Local Deep Stockfish"`.
    

## Why this matters

B3 currently creates a special exception to the ordinary strong-human-move approach.

Normally the intended Black-move process is:

```text
rank strong human moves
→ verify them with engines
→ choose the first one that is good enough
```

But current B3 says:

```text
top engine line shows mate
→ ignore all human candidates
→ run deep Stockfish
→ take Stockfish's top move
```

We have decided that this takeover is too broad.

The ordinary generation flow should still prefer a valid strong human move where possible, while using explicit Lichess mate information in a simple, deterministic way.

More extensive tactical and mate checking will happen later in a separate deep verification pass.

## Intended behaviour

`Known:` Normal generation should **not** have a general mate/tactical takeover mode that bypasses the human-candidate sieve.

The ordinary strong-HCM process remains the main selection algorithm.

Deep tactical and mating verification belongs mainly to the separate post-generation polishing pass.

## Lichess mate handling

`Known:` Lichess mate information can still be used directly because Lichess explicitly supplies mate distance.

If Lichess's returned moves contain forced mates for Black, rank those mating moves by **shortest mate distance**.

For example:

```text
...Qh2+   #3
...Rf1+   #3
...Qg2    #5
```

The shortest mate distance is `#3`.

Both `...Qh2+` and `...Rf1+` are therefore equally acceptable from the mate-distance point of view.

`Known:` If the current HCM has the same shortest mate distance as Lichess's best mating move:

> ACCEPT.

`Known:` If the HCM has a longer forced mate:

> REJECT.

`Known:` If Lichess's top result is a forced mate but the HCM has only a normal cp evaluation:

> REJECT.

`Known:` If Lichess's top result is a forced mate and the HCM is absent from the returned Lichess list:

> REJECT immediately.

Do not continue to ChessDB for that HCM.

Explicit Lichess mate information takes precedence over the ordinary cp waterfall.

So the mate branch is:

```text
Lichess top result is mate
        ↓
find shortest mate distance
        ↓
HCM has same shortest mate distance?
        ↓
yes → ACCEPT
no  → REJECT
```

## Equal mating moves

`Known:` If several Lichess moves have the same shortest mate distance, treat them as equally acceptable for human-candidate verification.

No extra tie-breaking rule is needed.

#note If all human candidates are rejected in such a mate position, trust Lichess's ordering among equal-length mates and use the first returned shortest-mate move.

## Final fallback in a Lichess mate position

`Known:` If every HCM is rejected while Lichess has explicitly identified a forced mate, use the **first Lichess move among the shortest mates**.

That differs from the ordinary non-mate final fallback.

Ordinary non-mate position:

```text
all HCMs rejected
→ Local Deep Stockfish top move
```

Explicit Lichess mate position:

```text
all HCMs rejected
→ first Lichess shortest-mate move
```

The reason is that Lichess has already supplied explicit mate-distance information, so there is no need to discard that information merely because no HCM matched it.

## ChessDB and mate handling

`Known:` ChessDB does not participate in mate-distance comparison.

We are not relying on ChessDB to tell us "mate in N", so it should not try to reproduce the Lichess mate rule.

ChessDB's ordinary cp values continue through the normal cp sieve.

We briefly considered using unusually large ChessDB advantages as a special tactical trigger, but discarded that idea.

`Known:` A large ChessDB cp difference is handled by the same ordinary HCM tolerance rules as any other non-mate evaluation.

If the HCM falls outside the threshold:

> reject it and continue normally.

Do not introduce a separate "large cp = tactical mode" shortcut.

## Separate deep tactical verification

#roadmap Add a separate post-generation polishing pass for tactical and mate verification.

For every chosen Black response:

1. run a deep local Stockfish search;
    
2. compare the saved move with Stockfish's top move;
    
3. apply the chosen tolerance;
    
4. if the saved response falls outside that tolerance, flag the position for review.
    

The purpose is to catch:

- missed tactics;
    
- forced mates;
    
- tactical resources that shallow/cloud evaluation did not expose clearly.
    

This pass should not automatically rewrite the repertoire.

It is a QA/polishing process.

Ideally it produces no flags.

## Bugs

#bug Current B3 bypasses the entire human-candidate process whenever its top baseline entry reports mate for Black. It immediately runs deep Stockfish and returns the engine's top move. The intended behaviour is narrower: explicit Lichess mate information should be used inside the same HCM-selection process, accepting HCMs with the same shortest mate distance and rejecting the others.

#bug If neither API list is available, B3 currently runs shallow local Stockfish at depth 18 / MultiPV 15 **before** the normal candidate loop simply to establish a baseline for the forced-mate check. Under the intended architecture, normal generation should not perform this extra pre-emptive local search merely to look for tactical/mate exceptions. Local Stockfish should be reached through the ordinary verification waterfall when actually needed.

#bug Current B3 may perform two local searches for the same position: first the shallow depth-18/MultiPV-15 mate baseline, then depth-24/MultiPV-1 after mate is detected. That special two-stage KILL MODE is not part of the intended generation architecture.

#bug The current forced-mate check looks only at the **first baseline entry** and asks whether that entry contains a negative mate value. It does not implement the intended comparison between the current HCM and all returned shortest mating moves.

#bug Current KILL MODE always chooses the deep local engine's top move after detecting mate. The intended Lichess-mate behaviour is to keep human preference where possible: an HCM with the same shortest mate distance should be accepted, and only if all HCMs fail should the first Lichess shortest-mate move be used.

## Notes

`Known:` Mate distance and centipawn loss are separate comparison systems.

Ordinary position:

```text
candidate cp loss
vs
cp threshold
```

Explicit Lichess mate position:

```text
candidate mate distance
vs
shortest mate distance
```

Do not try to convert a mate score into a cp threshold.

`Known:` ChessDB mate information is not required for this architecture.

`Known:` The later deep polishing pass is the safety net for tactical/mating inaccuracies that the normal generation flow may miss.
