### A4.27 — Put the position after Black's reply on the BACK of the queue, carrying its node ID, move number + 1, the new cumulative probability, the extended history, and the trap counter

**What the code does**  
The generator adds the position after Black's reply to the **back of the breadth-first queue** using `queue.push(...)`.

It puts these values into the queued item:

- `nodeId`: the repertoire node after Black's reply;
    
- `fen`: the board after Black's reply;
    
- `currentMoveNumber`: the current move number plus `1`;
    
- `trapDepth`: the value calculated by the rule described in [[A4.28]];
    
- `cumulativeProb`: `incomingPathProb`;
    
- `history`: the complete `blackHistory`.
    

For example, suppose the current queued position carries:

- move number `3`;
    
- cumulative probability `0.12`;
    
- history `d4 d5 c4 e6`.
    

White plays `Nc3`, and Diagram B chooses `Nf6`.

After [[A4.23]], the history is:

`d4 d5 c4 e6 Nc3 Nf6`

A4.27 then queues that resulting position approximately as:

```text
nodeId: node after ...Nf6
fen: position after ...Nf6
currentMoveNumber: 4
cumulativeProb: probability of reaching this line
history: d4 d5 c4 e6 Nc3 Nf6
```

Because `queue.push()` adds it to the back, any positions that were already waiting in the queue stay ahead of it. The generator therefore continues breadth-first rather than immediately following this one branch deeper.

The `cumulativeProb` carried forward is the probability calculated earlier in [[A4.32]]:

current position probability × White move probability.

Black's reply does not reduce it further because the repertoire chooses one Black response rather than assigning probabilities across alternative Black replies.

After queueing the position, the algorithm continues to [[A4.29]].

**Why this matters**  
This is what allows the newly completed White-and-Black line to become a future position for the generator to process.

The queued item carries everything A1/A2 need when it eventually reaches the front:

- which repertoire node it belongs to;
    
- the actual board;
    
- how deep the line is;
    
- how probable this exact route is;
    
- the exact move history;
    
- whether it is inside a trap/threat continuation.
    

Putting it at the back is also what gives the generator its breadth-first behaviour.

**Why it may have been designed this way**  
Likely: breadth-first processing lets the generator cover many shallower repertoire positions before going deeper into one particular line.

Carrying the full state in each queue item means the later iteration does not need to reconstruct the branch from scratch.
