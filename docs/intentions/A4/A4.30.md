### A4.30 — Loop back to A4.01 for the next included White move

**What the code does**  
After [[A4.29]] finishes, the current iteration of the White-move loop ends.

The generator is inside:

`for (const whiteMove of whiteCandidates)`

So control naturally returns to the top of that loop and takes the next included White move from the list.

Conceptually, that means returning to [[A4.01]] / [[A4.02]]:

- check whether another included White move remains;
    
- if yes, process it through A4;
    
- if no, leave the White-move loop.
    

There is no explicit jump statement at A4.30. The loop structure itself performs the return.

If another White move exists, processing begins again with that move.

If no White moves remain, the `for` loop ends and the generator proceeds to the per-node checkpoint handled outside A4.

**Why this matters**  
A4 processes **all included White moves from the current position**, not just the first one.

Each White candidate gets its own:

- resulting position after White;
    
- Black response or saved response;
    
- repertoire moves;
    
- training card;
    
- queued continuation.
    

Only after every included White move from this position has been dealt with does the generator finish the current node.

This is also why the resulting positions are put on the queue rather than followed immediately: A4 first finishes processing the current position's complete list of White candidates.

**Why it may have been designed this way**  
Likely: the generator needs to build every repertoire branch that survives the White-move filter before moving on to positions waiting in the breadth-first queue.

The ordinary `for` loop provides that behaviour without needing an explicit jump.
