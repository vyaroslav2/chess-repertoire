### A4.16 — -> Diagram B: pick Black's reply

**What the code does**  
This box is reached when [[A4.14]] finds that the position after White's move does not already have a saved training card with a chosen Black reply.

A4 now hands the position to Diagram B so that the programme can choose Black's response.

In the code:

`const algoResult = await evaluateBlackMove(fenAfterWhite, tempChess, node.currentMoveNumber, newHistory);`

It passes:

- the FEN after White's move;
    
- the temporary chess-board object already showing that position;
    
- the current full-move number;
    
- the move history including White's move.
    

A4 waits for Diagram B to finish and receives a result containing the selected Black move, if one was found, together with evaluation and human-data information used later in A4.

A4.16 itself does not decide which Black move is best.

That decision belongs entirely to Diagram B.

When B returns, A4 continues to [[A4.19]], which checks whether B actually found a move.

**Why this matters**  
This is the boundary between two responsibilities.

A4 has already decided which White move is being covered and has established the position where Black must respond.

Diagram B is responsible for deciding what that Black response should be.

Keeping the Black-move-selection logic separate means A4 does not need to know how B combines human statistics, engine evaluations or its other decision rules.

A4 only needs the result.

**Why it may have been designed this way**  
Likely: Black-move selection is complicated enough to be treated as its own algorithm.

Separating it into Diagram B keeps A4 focused on building and updating the repertoire tree, while B focuses on choosing the actual response.
