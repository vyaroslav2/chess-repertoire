### A4.29 — Wait 100 milliseconds

**What the code does**  
The generator pauses for `100` milliseconds[^1]:

`await delay(100);`

This happens after:

- the Black reply has been saved;
    
- the training card has been saved;
    
- the resulting position has been added to the back of the queue.
    

The comment in the code says:

`// Shorter delay since we hit cache!`

But this particular branch is the one where Diagram B was actually run, so that comment does not accurately describe what just happened here.

After the delay finishes, the algorithm continues to [[A4.30]].

**Why this matters**  
The delay does not change the repertoire, probability, queue order, or chess logic.

It only slows execution by one tenth of a second after each newly processed White move that reaches this path.

So if 100 such moves are processed, these waits alone add roughly 10 seconds to the run.

**Why it may have been designed this way**  
Likely: the delay was added to avoid making external/API-related work run too aggressively, or as a simple throttling measure while the generator was being developed.

However, by the time A4.29 runs, the external evaluation work for this move has already happened in Diagram B. The delay itself is therefore just a general pause between iterations rather than protection around a specific request.

Notes:

[^1]: #bug The 100 ms delay was intended to help avoid external API rate limits, but it happens only after Diagram B and all of its API/evaluation work have already finished. It therefore does not throttle the requests it was meant to protect. Rate limiting should happen at the actual API-call layer, before or between requests, rather than here after the move has already been processed.
