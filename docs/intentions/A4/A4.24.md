### A4.24 — Find or create the position-cache entry after Black's reply. Then look for a repertoire node using the exact extended move history. Create it if missing; otherwise raise its cumulative probability to the larger of its current value and ours

**What the code does**  
The generator first makes sure the shared position-cache entry exists for the board after Black's reply:

`await getOrCreatePositionCache(fenAfterBlack, undefined, blackHistory);`

That helper normalises the FEN before looking up or creating the `PositionCache` row.

The generator then looks for a repertoire node using the **exact move history**, not the FEN:

`let posAfterBlackNode = await getRepertoireNode(repertoire.id, blackPgn);`

`getRepertoireNode()` searches by the combination of:

- the repertoire ID;
    
- the exact PGN/history string.
    

So two different move histories that reach the same board are treated as different repertoire nodes at this particular lookup.

If no node exists for this exact history, the generator creates one:

`createRepertoireNode(repertoire.id, fenAfterBlack, blackPgn, incomingPathProb)`

The creation helper normalises the FEN before storing it, but the repertoire node still keeps this particular `blackPgn` history.

If a node with this exact history already exists[^2], the generator does not create another one. Instead, it updates its `cumulativeProb` to:

`Math.max(posAfterBlackNode.cumulativeProb, incomingPathProb)`

So the current code keeps the larger of:

- the probability already stored on this exact-history node;
    
- the probability calculated in the current run.
    

After that, the algorithm continues to [[A4.25]].

**Why this matters**  
This box behaves differently from the transposition lookup after White's move.

[[A4.08]] is intended to recognise the same chess position across different routes.

A4.24, however, searches by the **exact history**. A different history that reaches the same board will not be reused here merely because its FEN matches.

That means this lookup is primarily protecting against creating the same exact repertoire path twice, rather than performing position-based transposition merging.

The shared `PositionCache` still recognises the board by normalised FEN, so several different repertoire paths can point conceptually to the same cached chess position while remaining separate repertoire nodes.

The `Math.max()` probability behaviour is part of the transposition/probability problem already recorded in [[A4.08]], so it does not need another bug entry here.

**Why it may have been designed this way**  
Likely: the exact-history lookup is intended to preserve the repertoire tree as a record of distinct move sequences while preventing the same sequence from being created twice.

The shared position cache handles reusable information about the chess position itself, while the repertoire node keeps the particular move history by which this branch reached it.
