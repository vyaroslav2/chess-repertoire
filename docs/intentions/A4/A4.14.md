### A4.14 — Does this node have a saved training-card record pointing to a chosen Black reply?

**What the code does**  
The generator looks for a saved training-card record for the repertoire node representing the position after White's move.

In the code:

`const existingStat = await prisma.repertoirePositionStat.findUnique(...)`

The lookup uses:

- the current repertoire ID;
    
- the ID of the node after White's move.
    

If a training-card record exists, it contains `targetMoveId`, which points to the Black reply previously selected for this position.

So:

- saved training-card record exists -> yes;
    
- no saved training-card record -> no.
    

If the answer is yes, the algorithm continues to [[A4.17]], where it tries to load and reuse the saved Black move.

If the answer is no, the algorithm continues to [[A4.16]], where Diagram B is asked to choose a Black reply.

**Why this matters**  
This check decides whether the generator can reuse a Black response that was already chosen earlier.

If the position already has a saved training card, there is normally no reason to run the Black-move-selection logic again.

If it has no card, the generator still needs to work out which Black move should be learned from this position.

So this box separates:

- "we already know our response here";
    
- "we still need to choose our response here".
    

The training card belongs to the position after White's move, because that is the position where the user must choose Black's response.

**Why it may have been designed this way**  
Known: an existing SRS card should reuse its already-selected Black response rather than repeatedly calling the API/engine and choosing the move again.

This avoids unnecessary work and keeps the trained response stable between generator runs unless the card is deliberately updated elsewhere.
