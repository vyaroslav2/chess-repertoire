### A4.08 — Look for a node in this repertoire that already has this exact board

**What the code does**  
The generator looks inside the current repertoire for an existing node whose FEN matches the position after White's move.[^2][^3]

In the code:

`let posAfterWhiteNode = await prisma.repertoireNode.findFirst({`  
`where: { repertoireId: repertoire.id, fen: fenAfterWhite },`  
`include: { stats: true }`  
`});`

So the lookup requires:

- the same repertoire;
    
- an exact FEN match.
    

It also loads any saved position-stat records belonging to the node, because the next box needs to know whether the found node already has a saved training card.

However, there is a mismatch in the current code.

[[A4.05]] produces a full FEN from chess.js. That FEN includes the halfmove clock and fullmove number.

But repertoire nodes are created through `createRepertoireNode()`, which first normalises the FEN and stores the shortened form without those two counters.

A4.08 does not normalise `fenAfterWhite` before searching.[^1]

So a node created by the current code is stored under a different FEN string from the one A4.08 searches for.

As a result, A4.08 normally fails to find an existing node even when the same board is already present in the repertoire.

If a node were found, the algorithm would continue to [[A4.09]].

If none is found, it continues to [[A4.10]].

**Why this matters**  
The purpose of this lookup is to detect that the same chess position has already been reached through another move order.

That is the basis of the transposition-merging logic.

But because the FEN formats do not currently match, the lookup does not perform that job correctly.

This makes the "existing node found" routes after this box unreachable for nodes created normally by the current code.

The diagram already records this behaviour.

**Why it may have been designed this way**  
Known: the intention is to recognise the same board when it is reached through a different move order, so the repertoire can reuse the existing node instead of creating a duplicate branch.

The current full-FEN versus normalised-FEN mismatch prevents that intention from working.

Notes:

[^1]: #bug A4.08 searches for the full FEN while nodes are stored under the normalised one, so the lookup never matches and the merge branch has never run. Do not fix this in isolation: making the lookup match would switch on merge code that has never executed and that computes probability as the maximum of the two paths rather than the sum, which is not the intended behaviour. Fix the lookup, replace the merge maths, and add per-path probability storage together — see the transposition roadmap item.

[^2]: #roadmap Transposition and card identity. Store the full FEN with each node (source of truth, with the history). Store the normalised FEN (four fields — layout, side to move, castling, en passant — no counters) as the lookup key. Two nodes are the same position when their normalised FENs match; castling and en passant are already part of that key, so they need no separate rule, and the move counters and history are deliberately excluded. On a first route, create the node, its card and its continuation. On a later route reaching the same position, record the route and add its probability contribution — no second card, no second expansion. Total position probability is the sum of the unique routes' contributions. Fixing [[A4.08]] to normalise before searching is the first step; the rest is new structure. 

[^3]: #deferred Threefold repetition is left out of position identity. Two histories reaching the same board may have different repetition counts, but repetition is a property of a line, not a position, and it barely arises in opening preparation. Merging on the normalised FEN alone therefore treats them as one position, which is intended. Revisit only if a repertoire ever runs deep enough that a repeated position needs to be studied differently from its first occurrence.
