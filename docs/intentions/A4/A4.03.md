### A4.03 — No White moves remain -> return to A1.24, which prints the node checkpoint; then continue at A1's loop top

**What the code does**  
This box is reached when A4 has finished processing every White move that survived A3.

In the code, there is no separate "return" statement here.

The `for (const whiteMove of whiteCandidates)` loop simply ends when there are no more candidates left.

Execution then continues with the per-position checkpoint in [[A1.24]].

That checkpoint prints the running totals for the node that has just finished.

After that, execution reaches the end of A1's `while (queue.length > 0)` loop and returns to its top, where the next queued position is taken if one exists.

**Why this matters**  
This marks the end of all work on the current position.

A single position can have several included White moves, and A4 processes each one separately.

Only after the last one has finished does the generator leave A4 and return to the wider breadth-first queue.

So there are two nested loops:

- A4 works through every included White move for the current position;
    
- A1 works through every position waiting in the queue.
    

[[A4.03]] is where the inner White-move loop finishes and control returns to the outer position loop.

**Why it may have been designed this way**  
Likely: the generator needs to finish every selected White move from one position before moving on to another queued position.

The source code gets this behaviour naturally from the nested `for` and `while` loops. The diagram makes the transition explicit so it is clear when A4 has finished and A1 resumes control.
