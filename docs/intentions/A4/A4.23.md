### A4.23 — Play Black's reply. Extend the history again

**What the code does**  
The generator plays the Black move selected by Diagram B on the temporary chess board:

`tempChess.move(algoResult.selectedMoveSan);`

That temporary board already contains the current White move from [[A4.05]], so after this operation it represents the position after the complete White-and-Black move pair.

The generator then reads the resulting full FEN:

`const fenAfterBlack = tempChess.fen();`

It also extends the move history again:

`const blackHistory = [...newHistory, algoResult.selectedMoveSan];`

So `blackHistory` contains:

- all moves that led to the parent position;
    
- the White move currently being covered;
    
- the selected Black response.
    

It also creates a space-separated version of that history:

`const blackPgn = blackHistory.join(" ");`

The original history arrays are not modified. A new history is created for this continuation.

The algorithm then continues to [[A4.24]].

**Why this matters**  
This produces the next complete position that can later return to the breadth-first queue.

Before this box, A4 is working with the position after White's move, where Black must respond.

After this box, Black has responded and the resulting position is ready to become the next White-to-move position in the repertoire.

Keeping the extended history alongside the resulting FEN preserves both:

- the exact chess state produced by the move;
    
- the repertoire route that led to it.
    

That becomes especially important for transpositions, debugging and future PGN/export work.

**Why it may have been designed this way**  
Likely: A4 needs both the resulting board state and the complete route before it can create or reuse the next repertoire node.

Using the same temporary chess object also avoids reconstructing the board between White's move and Black's reply.
