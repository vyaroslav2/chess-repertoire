### A4.20 — Count this move under its tag — mainline, trap, or threat. If it is a trap or threat, also print the corresponding [TRAP] (Skipped) or [THREAT] (Skipped) message. Put the resulting position on the BACK of the queue, carrying: its node ID, move number + 1, the new cumulative probability, the extended history, and the trap counter updated by the same rule as A4.28. Add one to the skipped count

**What the code does**  
This box is reached after [[A4.17]] has reused the Black reply already stored on the training card and played it on the temporary board.

The generator first updates the same White-move category counters used on the newly generated branch:

- if it is a mainline, add `1` to the mainline count;
    
- if it is a trap, add `1` to the trap count;
    
- if it is a threat, add `1` to the threat count.
    

For a trap or threat, it also prints a skipped message saying that this flagged move was already in the database.

Trap/threat behaviour is deferred, so the important ordinary behaviour here is that reused moves still contribute to the generator's summary counters.

The generator then puts the position after the saved Black reply on the **back of the queue** with:

- `nodeId`: the destination node already stored on the saved Black move;
    
- `fen`: the board after playing that saved Black reply;
    
- `currentMoveNumber`: current move number + `1`;
    
- `trapDepth`: updated using the same rule as [[A4.28]];
    
- `cumulativeProb`: the newly calculated `incomingPathProb`;
    
- `history`: the existing history extended with White's move and the saved Black response.
    

The important detail is that it reuses:

`dbBlackMove.toNodeId`

It does **not** create another node after Black's reply on this path. The saved Black move already points to the existing destination node.

The generator then adds `1` to `totalSkippedMoves` and executes `continue`, which immediately returns to the White-candidate loop for the next included White move.

**Why this matters**  
This is the efficient reuse path.

Once the position after White already has a saved training card and Black response, the generator does not:

- call Diagram B again;
    
- recreate the Black move;
    
- recreate the training card;
    
- recreate the position after Black.
    

Instead, it follows the already stored Black move to its existing destination and queues that continuation for later processing.

The newly calculated `incomingPathProb` is still carried in the queued item. So although the chess continuation is reused, the current route's probability travels forward with this queue entry.

**Why it may have been designed this way**  
Likely: once a training position already has its chosen Black response, regeneration should reuse that response and continue deeper from it rather than repeating expensive evaluation work.

Using the saved move's `toNodeId` also preserves the already built repertoire structure.
