### A1.18 — Have we seen this history already?

**What the code does**
The line of text from [[A1.17]] is looked up in the visited list. If it is there, the item is dropped and the loop goes straight back to [[A1.14]] for the next one. If it is not, the run carries on and records it at [[A1.19]].

Dropping is silent. Nothing is printed, and no counter is raised.

**Why this matters**
If a repeated line did get through, the run would fetch the same statistics and repeat the same engine work before failing at node creation — the database would refuse a node whose history already exists, and the run would stop. So the check turns a crash into a skip.

Under normal working this check should never match. Each item added to the queue carries a different sequence of moves, so the list should stay ahead of it. It is a safeguard against something upstream queueing the same line twice, not a saving.

Because dropping is silent, a run gives no sign that it happened at all.[^1]

The check is on the *sequence*, so two move orders reaching the same board are both expanded — consistent with everything else, and the reason the same position can be evaluated more than once in a run. Whether that is wanted is the merging question, which belongs to [[A4]].

**Why it may have been designed this way**

Likely: written as an ordinary "don't do this twice" guard rather than as a safeguard, which would explain the silence. Nothing suggests the case was expected to occur.

**Also affects:** [[A1.17]] (which produces the text), [[A1.19]] (which records it), [[R.12]] (where the list is started), [[A1.14]] (where a dropped item returns to)
