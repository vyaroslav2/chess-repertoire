### A1.21 — Position in hand → A2: should we expand it?

**What the code does**
At this point the generator has taken one position from the front of the queue, confirmed that this move history has not already been dealt with during this run, recorded it as seen, counted it, and printed its current status.

It now carries that position forward into the next part of the algorithm: A2.

Nothing about the position is changed at this box. It is a hand-off.

A2 receives the same queued item, including:

- the board position;
    
- the database node ID;
    
- the current full-move number;
    
- the trap/threat continuation depth;
    
- the cumulative probability;
    
- the move history.
    

A2 then decides whether the branch is still allowed to continue before any White moves are fetched or considered.

**Why this matters**
This box marks an important boundary in the generator.

Everything before it is concerned with getting a position ready to be worked on: taking it from the queue, checking whether it has already been seen, recording it and reporting progress.

Everything immediately after it asks whether the generator should spend more work on that position at all.

That means a position can be counted as processed in [[A1.19]] and printed in [[A1.20]], but then be rejected by A2 without producing any new repertoire moves.

So "position in hand" does not mean "position will be expanded". It means only that this is the next position the generator is considering.

**Why it may have been designed this way**
Likely: the diagram separates queue management from expansion rules because they answer different questions.

A1 decides which position comes next.

A2 decides whether that position is allowed to grow further.

Keeping those ideas separate makes the breadth-first queue behaviour independent from the rules that limit depth.
