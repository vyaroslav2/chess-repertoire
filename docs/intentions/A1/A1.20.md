### A1.20 — Print the running status

**What the code does**
Three lines are printed for every position the run takes on, before any work is done on it.

The first gives the queue size, the move number, and the trap depth — but only when the trap depth is above zero. The second gives the history, the line of moves reaching this position. The third gives the elapsed time, the positions counted so far, and the number of evaluations that came back with no engine score.[^2]

All three go to the screen and into the log, since this is ordinary printing and [[R.06]] captures it.

**Why this matters**
This is the running commentary, and it is your only view of a run in progress. The generator does not return until it has finished, so these lines are how you tell whether it is working, where it has got to, and whether it is slowing down.

The queue size is the most useful of them. Watched over time it tells you whether the run is growing or winding down: rising means each position is producing more work than it consumes, falling means the end is in sight.[^3]

Because the history is printed in full, the log doubles as a record of every line the run looked at, in order. That is what makes a saved log worth comparing against another one.

The trap depth appearing only when it is above zero is a small kindness that also hides information: you cannot tell from a line whether the trap depth is zero or whether the field was omitted. In practice they mean the same thing, so nothing is lost.

Three lines per position, several hundred positions, is a large log. That was the reason for the wipe at the start, and it is why keeping three runs rather than all of them is the right trade.[^1]

Two of the three figures printed — positions counted and evaluations with no score — are running totals, while the rest describe this position.[^4] 

**Why it may have been designed this way**
Known: this is printed before the filtering, so a position that gets abandoned still appears in the log along with the reason, printed by [[A2]]. That is deliberate and useful — you can see what was rejected as well as what was kept.

**Also affects:** [[R.06]] (which puts these lines in the log), [[A1.19]] (which raises the counter printed here), [[A1.24]] (the fuller checkpoint printed after each position), [[R.02]] (the log these fill)

[^1]: #note Three lines per position means a run of a few hundred positions produces a long log. Keeping three runs rather than all of them, as decided in [[R.02]], is what stops the folder growing without limit.

[^2]: #roadmap Replace the running "no engine score" total on this line with the evaluation for this position: the score and where it came from. [^3]: #roadmap Print the queue's running maximum beside its current size, so a single line shows whether the run is still growing or winding down. Today the size alone is only meaningful when compared with the line before it.

[^4]: #roadmap Separate the per-position figures from the running totals on the status line. Put them in clearly distinct places — two lines, or a visible divider — so each is read at a glance. Fold this into the same layout change as the evaluation-and-source and queue-maximum items already on this box, since all three reshape the same lines.
