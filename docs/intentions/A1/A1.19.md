### A1.19 — Record it and count it

**What the code does**
Two things, one after the other. The line of text is added to the visited list, so this history will be recognised if it ever arrives again. Then the positions-processed counter goes up by one.

Both are in memory only. Neither survives the run.

**Why this matters**
The recording is what makes [[A1.18]] work at all. A safeguard that never records anything would never catch anything.

The counting is the more interesting half. This is where "positions processed" gets its meaning, and the meaning is narrower than the name suggests: it counts positions *taken off the queue and not skipped* — not positions expanded, not nodes created, not moves covered. A position counted here might still be abandoned moments later by the depth or trap limits in [[A2]], or turn out to have no White moves worth covering in [[A3]].

So the summary's headline figure is really "positions the run looked at", which is a fair measure of how much work was attempted but not of what was built. What was built is better read from the counts of White moves found and Black replies evaluated, or from the tree itself.[^1]

The count going up here, before any of the filtering, is also why it can be much larger than the number of nodes in your tree. That is not an error, but it is easy to misread.

**Why it may have been designed this way**
Known: recording before the expensive work rather than after it is correct — a position that fails halfway through should still not be attempted twice.

Likely: the counter was put here because it is the natural "we are dealing with this one now" moment, rather than as a decision about what the figure should mean.

**Also affects:** [[A1.18]] (which reads the list), [[R.12]] (where the list is started), [[A1.25]] (where the counter is set to zero), [[A1.20]] and [[A1.24]] (which print it), [[A1.15]] (the summary)

    It counts positions taken off the queue — the ones the run began working on, whether or not anything came of them. The count happens just after the visited check in [[A1.18]], so a position dropped there is never counted; since that check should never fire, in practice the figure is simply how many positions came off the queue.

    Nothing else has happened at that point. The filtering is all still to come, so a counted position may be abandoned in [[A2]] or produce nothing in [[A3]]. The figure measures work attempted rather than tree built, and is normally larger than the number of nodes.

    Worked example, a run with a depth cap of 3. The root comes off and is counted: 1. It yields four White moves worth covering, each with a Black reply, so four positions join the queue. Those four come off in turn: 5. One is a rare line whose cumulative probability has fallen too low, so [[A2]] abandons it — already counted. Another has no White move that clears the bar in [[A3]], so nothing is built from it — also already counted. The remaining two yield three replies each, six more positions, all counted as they come off: 11.

    The run reports 11, the tree gained fewer nodes than that, and two of the eleven produced nothing at all. Every figure is correct; only the name misleads.
