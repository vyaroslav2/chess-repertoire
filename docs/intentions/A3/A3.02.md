### A3.02 — -> F: get human moves for this position

**What the code does**  
The generator sends the current position's FEN to the shared human-move-fetching flow, [[F.01]].

In the code, this is:

`const [masters, elite, amateur] = await fetchAllDatabases(node.fen);`

The generator waits for F to finish and receives three results back:

- Masters;
    
- Elite;
    
- Amateur.
    

Each result contains the human moves available from that source and its total game count. The Masters response also provides the opening name and ECO code for the position; the handling and storage of that information is covered in F.

A3.02 itself does not decide whether to use cached data or contact Lichess. Those decisions happen inside the F flow.

F first looks for cached rows for all three databases. If all three are available, it rebuilds the results from the cache and returns them.[^2] Otherwise, it goes through the Lichess-fetching path and then returns whatever Masters, Elite and Amateur results were obtained.

Once the three results come back, A3 continues to [[A3.03]].

**Why this matters**  
A3 needs human-game information before it can decide which White moves are worth covering.

The three returned datasets are used by later A3 boxes for different purposes, including:

- building the pool of White moves;
    
- working out move popularity;
    
- identifying Master Threats and Amateur Traps;
    
- deciding which moves survive the White-move filter.
    

A3 does not need to know whether those results came from the local cache or from fresh Lichess requests. That fetching and caching behaviour is kept inside F.

**Why it may have been designed this way**  
Likely: the human-data fetching was separated into a shared flow so the generator can ask for the three datasets as one operation without duplicating the caching, retry and API logic inside A3.

That keeps A3 focused on deciding what to do with the returned move data rather than on how the data was obtained.
