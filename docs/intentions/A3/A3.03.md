### A3.03 — -> PC: get or create the position row for this position, passing the opening name and code from the masters result, and the move history

**What the code does**  
The generator sends the current position to the shared position-cache flow, [[PC.01]].

It passes:

- the current position's FEN;
    
- the opening information returned with the Masters result;
    
- the move history that led to this position.
    

In the code, this is:

`await getOrCreatePositionCache(node.fen, masters.opening, node.history);`

The PC flow then gets or creates the `PositionCache` row for this chess position.

If the row does not already exist, PC can create it with:

- the normalised FEN;
    
- ECO, if supplied;
    
- opening name, if supplied;
    
- Wikibooks opening text, if it can be found.
    

If the row already exists, PC may add opening metadata and opening text when the conditions in the PC flow allow it. The detailed create/update rules belong to the PC intentions rather than A3.03.

A3 does not use the returned `PositionCache` row here. The call is made for its database side effect: making sure the shared cached record for this position exists and is enriched where possible. The generator then continues to [[A3.04]].

**Why this matters**  
This stores information about the chess position independently of the repertoire tree.

That means information such as the position's FEN, ECO, opening name and opening text can live in one shared cached record rather than being tied only to one particular repertoire branch.

Passing the move history also gives PC enough context to look for opening text using the moves that led to the position.

The detailed rules for when opening metadata is written, updated or left unchanged are handled by PC, so A3 does not need to duplicate that logic.

**Why it may have been designed this way**  
Likely: position information that can be shared across repertoire branches was separated from the generator's move-selection logic.

A3 only needs to say, in effect, "make sure we have the shared cached record for this position". PC owns the details of normalising the FEN, creating the row and enriching it with opening information.
