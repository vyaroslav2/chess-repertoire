### A2.10 — Is the full-move number greater than the effective depth limit?

**What the code does**  
The generator compares the current position's full-move number with the effective depth limit calculated in [[A2.08]].

The check is strictly:

`currentMoveNumber > effective depth limit`

So:

- greater than the limit -> yes;
    
- exactly equal to the limit -> no;
    
- below the limit -> no.
    

The root position starts with full-move number `1`.

Whenever a Black reply is completed and the resulting position is added to the queue, the full-move number is increased by `1`.

So this number advances once per complete White-and-Black move pair.

If the answer is yes, the algorithm goes to [[A2.12]] and stops this branch.

If the answer is no, the position has passed the ordinary depth-limit check and the algorithm continues to [[A2.17]], which checks the separate trap/threat continuation limit.

**Why this matters**  
The effective depth limit is inclusive.

For example, if the effective limit is `3`:

- full-move number `1` -> allowed;
    
- full-move number `2` -> allowed;
    
- full-move number `3` -> allowed;
    
- full-move number `4` -> too deep.
    

This means the generator is allowed to process positions at the limit itself. It stops only when it reaches a position whose full-move number is greater than that limit.

With the current caller limit of `3`, this comparison is currently the point that actually enforces the overall depth cap.

In the current code, passing this check is required before the trap/threat continuation check in [[A2.17]] is even reached. If the ordinary depth limit has already been exceeded, the branch is stopped immediately at [[A2.12]].[^1]

**Why it may have been designed this way**  
Known: using a strict "greater than" comparison makes the effective depth limit inclusive. A position at the limit itself is still processed; only a position beyond it is considered too deep.
