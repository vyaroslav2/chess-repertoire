### A2.08 — Take the smaller of this budget and the caller's depth limit

**What the code does**  
The generator now compares two depth limits:

- the probability-based budget chosen in [[A2.05]], [[A2.07]] or [[A2.06]];
    
- the `maxDepth` value supplied by the caller.
    

It keeps whichever number is smaller.

In the code, this is:

`dynamicMaxDepth = Math.min(dynamicMaxDepth, maxDepth)`

So the probability-based budget can never make the generator go deeper than the caller allows.

The current launcher passes `3`, while the probability-based budgets are `15`, `8` and `5`.

That means the effective depth limit is currently always `3`, regardless of which probability range the position belongs to. The diagram explicitly notes this.

The resulting effective limit is then used by [[A2.10]].

**Why this matters**  
This makes the caller's depth limit a hard upper bound.

For example:

- probability budget `15`, caller limit `3` -> effective limit `3`;
    
- probability budget `8`, caller limit `3` -> effective limit `3`;
    
- probability budget `5`, caller limit `3` -> effective limit `3`.
    

So, with the current caller value, the probability-based depth system has no practical effect on how deep the generator goes.

The probability checks and budgets still run, but all three paths are reduced to the same effective limit before the actual depth test.

If the caller later supplied a larger value, the probability-based budgets would start to matter.

**Why it may have been designed this way**  
Known: this gives the generator two layers of control.

The probability-based budget decides how much depth a branch deserves according to how common it is.

The caller's limit provides an overall safety cap so that a run can be restricted regardless of those branch-specific budgets.
