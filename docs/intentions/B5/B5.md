# B5 — Package the selected Black response and return it to A4

## What the code does

B5 sits at the end of the Black-move selection flow.

By the time control reaches B5, the move-selection work should already be finished in [[B1]], [[B2]], [[B3]] and [[B4]].

B5 should not make another chess decision.

Its job is to take the already-selected Black response, package the final result, and return it to A4.

Conceptually:

```text
B1–B4
→ choose and verify Black response
→ final selected move is fixed

B5
→ package selected response
→ return to A4
```

## Why this matters

B5 is the boundary between:

- deciding which Black move to use;
    
- storing and continuing with that decision.
    

If B5 contains another fallback, re-ranking rule or hidden replacement rule, then the move returned to A4 may differ from the move the verification pipeline actually selected.

So B5 must remain simple.

## No move-selection logic

`Known:` B5 is a pure packaging and return step.

It does not:

- choose another Black move;
    
- re-rank candidates;
    
- re-run the verification waterfall;
    
- replace the selected move;
    
- invent another fallback;
    
- silently recover from missing selected-response data.
    

If essential data is missing when B5 is reached, that means an earlier stage failed.

So:

```text
selected move missing
→ HARD ERROR

selected evaluation missing
→ HARD ERROR

required provenance missing
→ HARD ERROR
```

B5 must not try to hide the earlier failure by choosing something else.

## Core B5 result

`Known:` B5 returns the selected Black response with these core fields:

```text
move
cp
mate
selectionSource
evaluationSource
selectionReason
engineRank?
deepVerified
```

The optional `engineRank` may be `null` when the exact engine rank is genuinely unknown.

## Move identity

`Known:` The authoritative move identity returned by B5 uses engine notation such as UCI/LAN.

For example:

```text
c7c6
g8f6
e7e5
```

SAN is not persisted in the B5 result.

SAN is derived later when needed for:

- logs;
    
- explanations;
    
- UI;
    
- other human-facing output.
    

So:

```text
authoritative move identity
→ UCI/LAN

human-readable notation
→ SAN derived when needed
```

This avoids maintaining two persistent notations that could drift out of sync.

## Evaluation fields

`Known:` B5 stores ordinary centipawn evaluations and explicit mate evaluations separately.

Use:

```text
cp
mate
```

For an ordinary evaluation:

```text
cp = -35
mate = null
```

For an explicit mate:

```text
cp = null
mate = 3
```

Mate values must not be converted into artificial centipawn values.

## Every repertoire move needs an evaluation

`Known:` Every repertoire move, for both White and Black, must have its own valid engine evaluation stored.

There are no exceptions for:

- hard-coded opening moves;
    
- human-selected moves;
    
- engine fallback moves;
    
- ordinary mainline moves;
    
- trap/threat moves later;
    
- White moves;
    
- Black moves.
    

The stored `cp` or `mate` must describe that exact move.

This is broader than B5, but B5 must enforce the invariant for the Black response it returns.

#roadmap Store a valid exact-move engine evaluation for every repertoire move on both sides. The rebuilt database must not contain repertoire moves without their own valid evaluation.

## Hard-coded opening responses

The deliberate first Black responses are:

```text
1.e4 → ...c6
1.d4 → ...d5
```

`Known:` These moves may bypass normal HCM selection, but they do not bypass evaluation requirements.

For example:

```text
move = c7c6
selectionReason = "Hardcoded opening"
selectionSource = "Hardcoded Opening"
evaluationSource = "Local Deep Stockfish"
```

The evaluation must belong specifically to `...c6`.

Likewise for `...d5`.

#bug The current hard-coded first-move path must not attach a general `bestCp` value if that score belongs to a different engine move. The saved evaluation must belong to the exact hard-coded move.

## Selection provenance versus evaluation provenance

`Known:` B5 keeps selection provenance and evaluation provenance separate.

These answer different questions.

### selectionSource

`selectionSource` means:

> Which verifier or selection mechanism caused this move to become the chosen repertoire response?

### evaluationSource

`evaluationSource` means:

> Which engine source supplied the stored evaluation for this exact move?

These may be the same.

For example:

```text
selectionSource = "ChessDB"
evaluationSource = "ChessDB"
```

But they do not have to be.

For example:

```text
selectionSource = "Hardcoded Opening"
evaluationSource = "Local Deep Stockfish"
```

The move was chosen because it is hard-coded, but Stockfish supplied the evaluation.

## Controlled source names

`Known:` `selectionSource` and `evaluationSource` use full controlled source names rather than arbitrary free text or project shorthand.

Current controlled names include:

```text
"Lichess Cloud Evaluation"
"ChessDB"
"Local Deep Stockfish"
"Hardcoded Opening"
```

This makes stored provenance understandable without needing to remember internal abbreviations.

## Selection reason

`Known:` B5 also stores a controlled `selectionReason`.

This describes why the move won the selection process.

Current controlled values include:

```text
"Human Candidate Move verified"
"Hardcoded opening"
"Local fallback"
"Shortest Lichess mate"
```

The reason is separate from the verification source.

For example:

```text
selectionReason = "Human Candidate Move verified"
selectionSource = "Lichess Cloud Evaluation"
```

or:

```text
selectionReason = "Human Candidate Move verified"
selectionSource = "ChessDB"
```

or:

```text
selectionReason = "Human Candidate Move verified"
selectionSource = "Local Deep Stockfish"
```

The reason remains the same because in all three cases the move won as the highest-priority Human Candidate Move that passed verification.

The exact verifier is already stored separately.

## Hard-coded opening reason

`Known:` Both deliberate first-move rules use:

```text
selectionReason = "Hardcoded opening"
```

Do not encode opening names into the selection reason.

Opening names already belong to position metadata elsewhere in the project.

So:

```text
1.e4 c6
→ selectionReason = "Hardcoded opening"
→ opening metadata belongs to the resulting position
```

and:

```text
1.d4 d5
→ selectionReason = "Hardcoded opening"
→ opening metadata belongs to the resulting position
```

This avoids prematurely calling `1.d4 d5` a Queen's Gambit Declined before the game has actually reached that opening.

## Engine rank

`Known:` B5 carries an optional informational `engineRank`.

It records the selected move's known custom rank within the engine source that actually verified or selected it.

It is useful for showing that the repertoire algorithm can choose an engine-safe practical move without simply choosing the engine's top move.

For example:

```text
selectionReason = "Human Candidate Move verified"
selectionSource = "Lichess Cloud Evaluation"
engineRank = 3
```

This means the selected human move was the third-ranked engine move in the trusted Lichess snapshot, but it was still safely inside the allowed threshold.

Likewise:

```text
selectionSource = "ChessDB"
engineRank = 2
```

## When engine rank is known

For a move selected from a trusted Lichess or ChessDB snapshot:

```text
engineRank
→ use the known custom rank from that snapshot
```

For final local deep fallback:

```text
Local Deep Stockfish top move
→ engineRank = 1
```

For a locally verified HCM that is also Stockfish's unrestricted best move:

```text
engineRank = 1
```

## When engine rank is unknown

During candidate-specific local verification, [[LS]] only needs:

```text
Stockfish best move
+
target HCM
```

If the HCM is not the best move, the programme knows only:

```text
HCM is not rank 1
```

It does not know whether the HCM is:

```text
rank 2
rank 3
rank 7
...
```

Therefore:

```text
locally verified non-top HCM
→ engineRank = null
```

Do not invent a rank.

Hard-coded opening moves may likewise have:

```text
engineRank = null
```

if their exact full-engine rank was never established.

`Known:` `engineRank` is informational only. It never feeds back into move selection.

## deepVerified

`Known:` `deepVerified` belongs to the selected move itself.

It means:

> This exact selected move has already been checked using the configured deep local Stockfish verification process.

It does not simply mean:

```text
evaluationSource = "Local Deep Stockfish"
```

Those are different facts.

For example, a move may have a local Stockfish evaluation without necessarily having gone through the full deep comparison process.

## When deepVerified is true

Examples include:

- a Human Candidate Move accepted after deep local verification;
    
- a final `"Local Deep Stockfish"` fallback move;
    
- a hard-coded opening move checked at the configured deep-local settings.
    

For example:

```text
move = c7c6
selectionReason = "Hardcoded opening"
selectionSource = "Hardcoded Opening"
evaluationSource = "Local Deep Stockfish"
deepVerified = true
```

only if that exact `...c6` move was actually checked at the configured deep-local settings.

## Local fallback

If all Human Candidate Moves are rejected in an ordinary position, [[B4]] chooses the top deep local Stockfish move.

B5 then packages something conceptually like:

```text
move = ...
cp = ...
mate = ...
selectionReason = "Local fallback"
selectionSource = "Local Deep Stockfish"
evaluationSource = "Local Deep Stockfish"
engineRank = 1
deepVerified = true
```

## Shortest Lichess mate

For the explicit Lichess mate case from [[B3]], B5 may receive a move selected because it is the first shortest-mate Lichess move.

That result uses:

```text
selectionReason = "Shortest Lichess mate"
selectionSource = "Lichess Cloud Evaluation"
evaluationSource = "Lichess Cloud Evaluation"
```

with explicit mate information stored in `mate`.

Do not convert the mate into cp.

## Human Candidate Move examples

### Verified by Lichess

```text
selectionReason = "Human Candidate Move verified"
selectionSource = "Lichess Cloud Evaluation"
evaluationSource = "Lichess Cloud Evaluation"
engineRank = known custom rank
deepVerified = false
```

unless that exact move was independently deep-verified elsewhere.

### Verified by ChessDB

```text
selectionReason = "Human Candidate Move verified"
selectionSource = "ChessDB"
evaluationSource = "ChessDB"
engineRank = known custom rank
deepVerified = false
```

unless that exact move was already deep-verified.

### Verified locally and equal to Stockfish's best move

```text
selectionReason = "Human Candidate Move verified"
selectionSource = "Local Deep Stockfish"
evaluationSource = "Local Deep Stockfish"
engineRank = 1
deepVerified = true
```

### Verified locally but not Stockfish's best move

```text
selectionReason = "Human Candidate Move verified"
selectionSource = "Local Deep Stockfish"
evaluationSource = "Local Deep Stockfish"
engineRank = null
deepVerified = true
```

The missing rank is deliberate and truthful.

## Threshold data is not persisted

`Known:` Verification thresholds and candidate-loss margins are decision data, not persistent repertoire metadata.

Do not store fields such as:

```text
candidateLossCp
allowedLossCp
```

on the B5 result.

Those values belong in:

- verification calculations;
    
- detailed logs;
    
- debugging output.
    

B5 stores the decision result, not every intermediate calculation that produced it.

## SAN belongs in logs

`Known:` SAN is not part of the persistent B5 payload.

If human-readable logging is needed, derive SAN from the position and UCI/LAN move and write it into the log.

For example:

```text
stored:
move = g8f6

log:
Selected ...Nf6
```

The log may be human-friendly.

The persisted move identity stays engine-native.

## Intended B5 flow

```text
receive final selected Black response
↓
verify required packaged data exists
↓
move present?
├─ no → HARD ERROR
└─ yes
    ↓
valid cp or mate present?
├─ no → HARD ERROR
└─ yes
    ↓
required provenance present?
├─ no → HARD ERROR
└─ yes
    ↓
package:
- move
- cp
- mate
- selectionSource
- evaluationSource
- selectionReason
- engineRank?
- deepVerified
    ↓
return to A4
```

B5 does not attempt another move-selection fallback anywhere in this flow.

## Bugs

#bug Any B5 or surrounding return path that can substitute another Black move when the selected result is incomplete must be removed. Missing required selected-response data is a hard error.

#bug The hard-coded opening path must not save an evaluation belonging to some other engine move. `...c6` and `...d5` require their own exact-move evaluations.

#bug Any persisted mixed evaluation field that forces cp and mate values into the same representation should be replaced with separate `cp` and `mate` fields.

#bug SAN should not be the authoritative stored move identity for the B5 result. Use UCI/LAN and derive SAN only for logs or other human-facing output.

## Notes

`Known:` B5 packages an already-final decision. It does not make another chess decision.

`Known:` UCI/LAN is the authoritative move identity.

`Known:` SAN is derived only for logs and human-facing output.

`Known:` cp and mate are stored separately.

`Known:` every repertoire move requires its own exact engine evaluation.

`Known:` selection provenance and evaluation provenance are separate.

`Known:` `selectionReason` explains why the move won.

`Known:` `selectionSource` explains which verifier or mechanism selected it.

`Known:` `evaluationSource` explains where the stored evaluation came from.

`Known:` `engineRank` is optional and informational only.

`Known:` unknown rank is stored as `null`, never guessed.

`Known:` `deepVerified` refers to the exact selected move, not merely to the existence of a local Stockfish evaluation.
