# B2 — Gather engine evaluations

## What the code does

B2 receives the ranked human-move shortlist from [[B1]].

Its present job is mainly to **gather engine scores for the position**. The actual loop that checks the individual human candidates against those engine scores happens later in the evaluator.

B2 first creates six working values:

- `enginePvs` — the main list of engine moves and evaluations;
    
- `chessdbPvs` — a separate list of ChessDB moves and evaluations;
    
- `bestCp` — the best evaluation from the current main source, initially `0`;
    
- `lichessCp` — the best Lichess evaluation, initially `null`;
    
- `chessdbCp` — the best ChessDB evaluation, initially `null`;
    
- `evalSource` — the source currently treated as primary, initially `"Lichess"`.
    

`cp` means centipawns. For example, `100 cp` is approximately one pawn.

`bestCp = 0` is only an initial placeholder. It does not mean the position has actually been evaluated as equal.

B2 then looks in `EngineEvalCache` for **all stored engine rows for the normalised position**, ordered by rank.

The current check is very broad:

> "Does this position have any stored engine scores?"

It does not first ask whether a complete Lichess snapshot or complete ChessDB snapshot exists.

### If cached rows exist

B2 separates them into:

- Lichess rows;
    
- ChessDB rows.
    

If Lichess rows exist, B2 uses them as the main list.

The first ranked Lichess row becomes:

- `bestCp`;
    
- `lichessCp`.
    

It then reconstructs the saved move list from the cache.

If no Lichess rows exist but ChessDB rows do exist, B2 changes the main source to `"ChessDB"`.

The first ranked ChessDB row becomes:

- `bestCp`;
    
- `chessdbCp`.
    

The cached ChessDB rows then become the main engine list.

If cached rows exist but they belong to neither recognised source, B2 still treats the position as having an engine cache hit, but neither list is reconstructed. The main list can therefore remain empty and `bestCp` can remain its placeholder `0`. The current diagram specifically notes that deep-local rows can produce this situation.

### If there are no cached engine rows

B2 waits one second.

It then checks `GlobalState.lichessCloudEvals`.

If that switch is on, it asks Lichess Cloud Eval for up to five PVs.

The current code requests:

`multiPv=5`

If Lichess returns usable moves:

- those moves become the main engine list;
    
- the top score becomes `bestCp`;
    
- the top score is also recorded as `lichessCp`;
    
- every returned Lichess move is saved to `EngineEvalCache` with its rank, evaluation and mate field.
    

However, `GlobalState.lichessCloudEvals` currently starts as `false`, and the current flow does not turn it on. So fresh Lichess Cloud Eval fetching is presently skipped.

B2 then asks ChessDB for its known moves from the position.

This happens on the current fresh-fetch path whether Lichess succeeded or not.

ChessDB is called directly rather than through [[FR]], so the current request does not share FR's retry handling.

For each ChessDB result, B2:

- reads the move;
    
- reads its score;
    
- flips the sign so the score uses the project's White-point-of-view convention;
    
- adds it to the separate ChessDB list;
    
- caches the move with its rank and evaluation.
    

The ChessDB mate field is deliberately stored as `null`.

The ChessDB list is then sorted so the lowest evaluation is best for Black.

The best ChessDB value becomes `chessdbCp`.

If Lichess supplied no usable main list, ChessDB also becomes the main source and its list is copied into `enginePvs`.

B2 then passes its gathered engine information onwards.

The current values carried forward include:

- the main engine list;
    
- the main best score;
    
- the separate ChessDB list;
    
- the selected source label;
    
- the Lichess top score, if available;
    
- the ChessDB top score, if available.
    

The current diagram then exits to [[B3]] for the forced-mate check.

## Why this matters

B1 has already ranked candidate Black replies according to strong human results.

The engine layer exists to answer a different question:

> "Is this strong human move objectively close enough to the engine's best move?"

The intended repertoire is therefore not simply:

> pick the engine's top move

and not simply:

> pick the highest-scoring human move.

The intended principle is:

```text
strong human preference
        ↓
engine safety check
        ↓
first human move that is good enough
```

Only if every suitable human move fails should the engine itself supply the repertoire move.

## Intended behaviour

`Known:` Lichess Cloud Eval is the first engine-verification source.

For each position, first check whether a trusted cached Lichess snapshot already exists.

If it does, reuse it.

If it does not, fetch Lichess before evaluating the human candidates.

One Lichess snapshot belongs to the **position**, not to one human candidate. The same snapshot is reused while checking every candidate from [[B1]]. There is no need to query the cache separately for each human move.

`Known:` Lichess may return fewer than five moves. Use however many valid moves it actually returned. The final returned move is the boundary move; never assume there are exactly five.

`Known:` A successful API response is trusted as the complete snapshot supplied by that source. Once it has been captured correctly and cached, normal generation does not refresh it.

`Known:` A successful response containing zero moves is a valid empty snapshot. Log a warning, remember/cache that result, and move to the next source.

`Known:` A failed fetch is not valid cache data. It should only be remembered as unavailable for this position during the current run.

`Known:` "One fetch attempt" means one **complete retry cycle**, which may contain several properly spaced HTTP requests. If that entire cycle fails, later human candidates must not start a new cycle for the same source.

### Lichess sieve

For each human candidate, use the Lichess snapshot first.

If the candidate is Lichess's top move:

> accept immediately.

If the candidate appears elsewhere in Lichess's returned list:

1. calculate its cp loss relative to Lichess's best move;
    
2. compare that loss with the threshold for the current full-move number;
    
3. within the threshold → accept;
    
4. outside the threshold → reject and move to the next human candidate.
    

A clear Lichess rejection is final for that candidate. ChessDB does not get an opportunity to overrule it.

If the candidate is **not** in Lichess's returned list, inspect the last returned Lichess move.

If that last move is already outside the threshold:

> the absent candidate must be at least as bad or worse → reject it.

If that last returned move is still inside the threshold:

> Lichess cannot tell whether the absent candidate is acceptable → continue to ChessDB.

For example:

```text
Best Lichess move:       0 cp loss
2nd:                    10
3rd:                    18
4th:                    25
5th:                    37

Threshold:              30
Candidate absent
```

The fifth move is already `37 cp` worse than best.

Therefore the absent candidate cannot be within the `30 cp` limit.

Reject it without calling ChessDB.

### ChessDB sieve

`Known:` ChessDB uses the same decision rule.

If the candidate is ChessDB's top move:

> accept.

If it appears in the ChessDB list:

> calculate its cp loss from ChessDB's best move and accept/reject using the threshold.

If it is absent:

- last returned ChessDB move outside threshold → reject;
    
- last returned ChessDB move still within threshold → inconclusive → local Stockfish.
    

A clear ChessDB rejection is final for that candidate.

Local Stockfish is only needed when ChessDB cannot decide.

ChessDB also uses a position-level cache.

The first human candidate that needs ChessDB may trigger a fetch/retry cycle.

If successful, cache the complete snapshot and reuse it for every later candidate.

If the cycle fails, remember ChessDB as unavailable for this position and send any later unresolved candidates directly to local Stockfish.

### Local Stockfish sieve

`Known:` Local Stockfish is the final verification source when both APIs are inconclusive or unavailable.

It only needs to answer:

> "Is this human candidate within the allowed loss from Stockfish's best move?"

The local threshold is intentionally slightly looser than the Lichess/ChessDB threshold to allow for fluctuations in local-engine evaluation.

The threshold depends only on the **full-move number**, not on candidate popularity, candidate rank or ply count.

The threshold values — both the API column and the looser local column — live in [[M]]. B2 applies whichever band matches the current full-move number; it does not define the numbers.

`Known:` If local Stockfish accepts the human candidate, save:

- that candidate;
    
- its local evaluation;
    
- source `"Local Stockfish"`.
    

If local Stockfish rejects it, continue to the next B1 human candidate.

### If every human candidate fails

`Known:` If every B1 human candidate is rejected, human preference is exhausted.

Run the deepest local Stockfish search available and choose its **top move**, even if that move has never appeared in human games.

Save:

- the engine's top move;
    
- its evaluation;
    
- source `"Local Deep Stockfish"`.
    

Log clearly that all human candidates were rejected and the engine fallback was used.

## Evaluation storage

`Known:` The chosen repertoire move needs only:

- its selected evaluation;
    
- the source of that evaluation.
    

For example:

```text
evaluation: +0.02
source: Lichess
```

If Lichess accepts the move, ChessDB does not need to be queried merely to obtain another evaluation.

If ChessDB accepts it, the selected source is ChessDB.

If local Stockfish accepts it, the selected source is `"Local Stockfish"`.

The source is retained for debugging and provenance but does not normally need to be displayed in the move-tree GUI.

Non-mate GUI evaluations should be shown in pawn units with two decimal places:

```text
+0.23
-1.17
+3.42
+10.23
```

Forced mate will use a separate `#N` representation.

Detailed acceptance calculations do **not** need to be duplicated on the repertoire move. They belong in the terminal/debug log.

## Debug logging

`Known:` Every engine-sieve decision should be visible enough to explain why a move was accepted or rejected.

Normal acceptance:

```text
[LICHESS]
Candidate: ...e6
Best: ...Nf6
Candidate eval: +0.02
Best eval: -0.10
Loss: 12 cp
Limit: 80 cp
ACCEPT
```

Normal rejection:

```text
[LICHESS]
Candidate: ...e6
Best: ...Nf6
Candidate eval: +0.42
Best eval: -0.10
Loss: 52 cp
Limit: 35 cp
REJECT
```

If the candidate is absent from the returned list:

```text
[LICHESS]
Candidate: ...e6
Candidate not in returned list
Last returned move: ...c6
Last-move loss: 41 cp
Limit: 35 cp
REJECT
```

If the source cannot decide:

```text
[LICHESS]
Candidate: ...e6
Candidate not in returned list
Last returned move: ...c6
Last-move loss: 21 cp
Limit: 35 cp
INCONCLUSIVE -> CHESSDB
```

A source failure should also state the fallback:

```text
[LICHESS]
Fetch failed after retry cycle
FALLBACK -> CHESSDB
```

```text
[CHESSDB]
Fetch failed after retry cycle
FALLBACK -> LOCAL STOCKFISH
```

A successful empty response should be visibly different:

```text
[WARNING] Lichess returned no moves
FALLBACK -> CHESSDB
```

This gives three distinct outcomes for the sieve itself:

- `ACCEPT`;
    
- `REJECT`;
    
- `INCONCLUSIVE`.
    

And three distinct API states:

- usable result;
    
- successful but empty result;
    
- failed fetch.
    

## Bugs

#bug B2.03 currently treats **any** engine-cache row for the position as a cache hit. The intended check is source-specific: determine whether a trusted Lichess snapshot exists, and independently whether a trusted ChessDB snapshot exists. A ChessDB or local-engine row must not make the Lichess cache appear complete.

#bug Fresh Lichess Cloud Eval is currently disabled because `GlobalState.lichessCloudEvals` starts as `false`. The intended flow always tries cached/fresh Lichess first and falls back to ChessDB only when Lichess is unavailable or inconclusive.

#bug ChessDB is currently fetched on every fresh engine-cache path even when Lichess has already provided enough information. Intended behaviour is candidate-driven: ChessDB should only be required when Lichess cannot decide the current human candidate.

#bug ChessDB currently bypasses [[FR]] and has no proper retry cycle. A ChessDB fetch should receive one complete retry cycle when first needed for the position. If that cycle fails, remember ChessDB as unavailable for that position and fall back to local Stockfish.

#bug The current engine-cache model does not reliably distinguish a complete trusted source snapshot from merely having one or more rows. Successful snapshots must be captured fully, including rank/order and explicit successful-empty state. Partial or unrelated rows must not count as a complete source response.

#bug Cache writes must preserve the complete successful snapshot. Missing returned rows, partial writes or stale rows from an older snapshot would violate the "fetch once, then trust the cache" model.

#bug The current final fallback can choose the top API move and can ultimately fall back to the first human candidate even though that human move was never successfully engine-verified. The intended final fallback after all human candidates fail is always the top move from `"Local Deep Stockfish"`. An unverified human candidate must never be allowed through.

#bug Fresh Lichess Cloud Eval currently receives the normalised four-field FEN. Under the already established FEN architecture, external API requests should use the full FEN while the normalised FEN is used as the global lookup/cache key.

## Roadmap

#roadmap Add a separate **post-generation deep-engine polishing pass**.

For every chosen Black repertoire response:

1. run a deep local Stockfish search;
    
2. compare the saved move against Stockfish's top move;
    
3. use the relevant threshold;
    
4. if the saved response is outside the threshold, flag the position for review.
    

The polishing pass does **not** automatically replace the response.

Its purpose is quality assurance: catch tactics, forced mates or other tactical resources that the shallower/cloud evaluations may have missed.

Ideally it should produce no flags.

#roadmap Preserve enough engine-source provenance for debugging while keeping the repertoire move itself simple: selected evaluation + selected source.

## Deferred

#deferred Do not build a special "large evaluation / possible forced mate" takeover rule into the ordinary human-candidate selection yet.

The normal generation algorithm should continue using the strong-human-candidate sieve.

Deep tactical/mate checking of the chosen responses will be handled by the separate polishing pass until that logic is deliberately redesigned.

## Notes

`Known:` Lichess and ChessDB verification are sufficient on their own. Once either source clearly accepts a candidate, do not run another engine merely for confirmation.

`Known:` A clear rejection by an earlier source is also sufficient. Lichess rejection means next human candidate; ChessDB rejection means next human candidate.

`Known:` Only an **inconclusive** result falls through to the next source.

`Known:` ChessDB mate information is not part of the required model. ChessDB cache rows may keep the mate field blank.

`Known:` Once a successful Lichess or ChessDB snapshot has been captured fully, trust it indefinitely. Normal generation does not make refresh calls.

`Known:` The engine cache is position-level; the local candidate verification is candidate-level.

`Known:` The final deep-engine fallback may choose a move with zero human support. That is the purpose of the fallback.
