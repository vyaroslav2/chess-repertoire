# B4 — Walk through ranked human candidates and choose the first verified RESPONSE

  

## What the code does

  

B4 currently receives the human-candidate shortlist ranked by [[B1]] and walks through those candidates in order.

  

Current code also contains:

  

```text

hard-coded first Black responses

Gemini first-move selection for some cases

Lichess / ChessDB / local verification paths

candidate-level try/catch behaviour

legacy local-engine reuse/fallback behaviour

```

  

Some of those current-code behaviours are obsolete.

  

The intended architecture below is the source for future implementation.

  

## Core principle

  

`Known:` Choose the highest-ranked human candidate move that is engine-safe.

  

B4 does not re-rank the B1 shortlist.

  

```text

HCM #1

→ verify

→ ACCEPT?

   ├─ yes → choose and stop

   └─ no  → HCM #2

```

  

## Human-candidate order

  

Process HCMs strictly in descending human score from [[B1]].

  

A rejected candidate does not change the scores or order of the remaining candidates.

  

The first HCM accepted by a valid verification layer wins.

  

## Verification waterfall

  

For each HCM:

  

```text

HCM

↓

Lichess Cloud Evaluation

├─ ACCEPT → choose HCM

├─ REJECT → next HCM

└─ INCONCLUSIVE / unavailable

      ↓

   ChessDB

   ├─ ACCEPT → choose HCM

   ├─ REJECT → next HCM

   └─ INCONCLUSIVE / unavailable

         ↓

      Local Deep Stockfish

      ├─ ACCEPT → choose HCM

      └─ REJECT → next HCM

```

  

A clear ACCEPT or REJECT from an earlier valid source is final for that HCM.

  

Do not ask later sources to overrule it.

  

## Remote cache reuse

  

`Known:` Remote source data is reusable only under its exact cache identity.

  

For Lichess/ChessDB:

  

```text

exact FullFen

+ source

+ evaluationProfile

```

  

identifies the fetch context.

  

A candidate evaluation additionally requires:

  

```text

candidate UCI/LAN move

```

  

If a successful matching remote fetch already exists:

  

```text

→ reuse it

→ do not query that same source/profile again automatically

```

  

## Candidate absent from a successful remote result

  

If:

  

```text

RemoteEngineFetch exists

+ candidate evaluation absent

```

  

the candidate is unavailable from that source's returned analysis.

  

Do not repeatedly re-query the same source/profile in the hope that it appears.

  

Use the normal PV/source-coverage rule and continue the waterfall where appropriate.

  

## Source failure

  

If a remote source is unavailable after its configured retry policy:

  

```text

→ that source cannot decide this candidate

→ continue to the next source

```

  

A malformed successful response is different.

  

Malformed trusted analysis is a hard error; do not hide it by silently falling through.

  

## Local Deep Stockfish

  

Local verification is candidate-specific.

  

Required cache identity:

  

```text

exact FullFen

+ checked candidate UCI/LAN

+ evaluationProfile

```

  

If compatible Local Deep evidence already exists:

  

```text

→ reuse it

```

  

Otherwise run the configured Local Deep analysis.

  

Compare:

  

```text

checked HCM

vs

Local Deep top move

```

  

using the shared local tolerance from [[B2]]/[[M]].

  

If Local Deep itself cannot produce valid required evidence:

  

```text

→ hard generation error

```

  

A technical engine failure must not look like a chess rejection.

  

## Empty HCM shortlist

  

If [[B1]] returns no HCMs:

  

```text

→ Local Deep Stockfish fallback

→ choose its top move

```

  

The selected move may have no human-game support.

  

That is intentional.

  

## All HCMs rejected

  

If every HCM is rejected:

  

```text

→ Local Deep Stockfish fallback

→ choose its top move

```

  

Do not fall back to an unverified human candidate.

  

## Hardcoded first responses

  

`Known:` The two deliberate first-move repertoire choices remain:

  

```text

1.e4 → 1...c6

1.d4 → 1...d5

```

  

They bypass ordinary HCM selection.

  

But hardcoding the move does **not** bypass evaluation.

  

Every finalised RESPONSE still needs an exact evaluation for that exact move.

  

Provenance:

  

```text

selectionMethod = "Hardcoded Opening"

moveOrigin = "Hardcoded Move"

```

  

Evaluation `source` is independent and must be one of:

  

```text

"Lichess Cloud Evaluation"

"ChessDB"

"Local Deep Stockfish"

```

  

`"Hardcoded Opening"` is not an evaluation source.

  

## Gemini

  

`Known:` Gemini is removed from chess move selection.

  

It must not choose:

  

```text

first RESPONSES

fallback RESPONSES

ordinary RESPONSES

```

  

Against first White moves other than `1.e4` and `1.d4`, use the normal B1 → verification-waterfall process.

  

## Evaluation meaning

  

Every stored RESPONSE evaluation means:

  

> the value of choosing this exact RESPONSE from this exact source FullFen

  

It is normalised to White-positive.

  

Do not attach the evaluation of one engine move to a different hardcoded or selected move.

  

#bug Current hardcoded first-move code can associate a general/best engine score with `...c6` or `...d5` even when that score belongs to another move.

  

## RESPONSE provenance

  

Persistent RESPONSE provenance uses:

  

```text

selectionMethod

moveOrigin

source

```

  

Do not persist the old free-text `selectionReason`.

  

Controlled `moveOrigin` values include:

  

```text

"Human Move"

"Engine Move"

"Hardcoded Move"

```

  

Controlled `selectionMethod` values include:

  

```text

"Ordinary API"

"Corrected after Deep Verification"

"Local Engine Fallback"

"Hardcoded Opening"

```

  

## deepVerified

  

`Known:` `deepVerified` is part of the intended RESPONSE state, not merely a roadmap idea.

  

It means:

  

> this exact current RESPONSE survived Deep Verification against the current stored Local Deep evidence for its exact FullFen and evaluation profile

  

### Starts false

  

A RESPONSE chosen only from remote evidence normally starts:

  

```text

deepVerified = false

```

  

It must eventually be checked by [[TS]].

  

### Already deep-verified during selection

  

If the exact selected HCM has already passed the same required Local Deep verification evidence during B4:

  

```text

deepVerified = true

```

  

If the final fallback is the Local Deep top move from the required deep analysis:

  

```text

deepVerified = true

```

  

provided the stored evidence is the same current Local Deep evidence required by DV.

  

### Invalidation

  

Changing the RESPONSE UCI/LAN invalidates verification.

  

Replacing the relevant Local Deep evidence for:

  

```text

FullFen

+ RESPONSE

+ evaluationProfile

```

  

also invalidates verification.

  

Refreshing only Lichess/ChessDB evidence does **not** clear `deepVerified` when:

  

```text

RESPONSE unchanged

FullFen unchanged

Local Deep evidence unchanged

```

  

## SAN/UCI conversion

  

UCI/LAN is authoritative move identity.

  

SAN may be derived/cached for display.

  

If conversion of a project-owned human candidate fails:

  

```text

→ hard error

```

  

Do not silently skip that HCM.

  

## Error handling

  

Technical/data errors must not be swallowed as ordinary chess rejections.

  

Hard errors include:

  

```text

illegal/unconvertible candidate move

malformed trusted engine evidence

invalid evaluation shape

Local Deep technical failure after its own retry/error policy

internal identity/invariant failure

```

  

#bug Current broad candidate-level try/catch can make technical errors look like rejected HCMs.

  

## Relationship to PV

  

[[PV]] answers:

  

> what does this one coherent remote engine result prove about this one HCM?

  

B4 owns the surrounding process:

  

```text

which HCM is current

which source is next

when selection stops

when fallback is required

```

  

## Result

  

B4 should implement:

  

```text

ranked HCM list

→ first HCM

→ Lichess

→ ChessDB if needed

→ Local Deep if needed

→ ACCEPT first engine-safe HCM

  

if none survive

→ Local Deep top move

  

hardcoded first response

→ keep deliberate move

→ obtain exact evaluation separately

  

all selected RESPONSES

→ exact move evaluation

→ structured provenance

→ correct deepVerified state

```
