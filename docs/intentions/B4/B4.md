# B4 — Walk through the ranked human candidates and choose the first verified Black reply

## What the code does

B4 receives the human-candidate shortlist ranked by [[B1]].

The candidates are already sorted from highest to lowest Black human score.

Before the normal candidate loop, the current code has special handling for Black's first move.

If White played:

- `1.e4`, Black is hard-coded to play `...c6`;
    
- `1.d4`, Black is hard-coded to play `...d5`.
    

These two repertoire choices bypass the ordinary HCM/engine-verification waterfall.

For other first White moves, the current code can use Gemini to choose a Black response before the ordinary candidate loop.[1](#user-content-fn-1)

If no move has been chosen by this special first-move handling, B4 processes the B1 human candidates one by one.

For each HCM, the current code converts the move into the notation needed for engine comparison and checks it against the available engine data.

The candidate is first checked against the main engine list.

If that check accepts the HCM, B4 chooses it and stops.

If it rejects the HCM, B4 moves to the next human candidate.

If it cannot decide, B4 tries ChessDB.

If ChessDB accepts the HCM, B4 chooses it and stops.

If ChessDB rejects it, B4 moves to the next HCM.

If ChessDB cannot decide, the current code falls back to local Stockfish.

The current local path uses one depth-18, MultiPV-15 search and can reuse that result for later HCMs from the same position.[2](#user-content-fn-2)

Candidate processing is currently wrapped in a `try/catch`. If some errors occur while converting or evaluating a candidate, the code can silently skip that HCM and move to the next one.[3](#user-content-fn-3)

If no HCM is selected, the current code first tries the top move from its main engine list.

If that is unavailable, it can fall back to the first human candidate even though that candidate was not successfully engine-verified.[4](#user-content-fn-4)

## Why this matters

B4 is where the human ranking from [[B1]] and the engine-verification rules from [[B2]] are combined.

The intended principle is:

> **Choose the highest-ranked human move that is engine-safe**

The engine does not re-rank the human shortlist.

Instead, B4 walks down the existing B1 order until one HCM passes verification.

## Intended behaviour

### Human-candidate order

`Known:` B4 processes the B1 human-candidate shortlist strictly in descending human-score order.

HCM #1 has the highest Black score, HCM #2 the second-highest, and so on.

The first HCM that passes a valid verification layer is selected immediately.

For example:

```text
HCM #1
→ REJECT

HCM #2
→ ACCEPT
→ choose HCM #2
→ stop
```

Do not examine HCM #3 or anything below it.

`Known:` Rejection is binary for the current HCM.

When an HCM is rejected:

- log why;
    
- move directly to the next HCM;
    
- do not re-rank the remaining moves;
    
- do not modify their human scores;
    
- do not carry a penalty forward.
    

## Verification waterfall for each HCM

Each HCM gets the same verification waterfall:

```text
HCM
 ↓
Lichess
 ├─ ACCEPT → choose HCM and stop
 ├─ REJECT → next HCM
 └─ INCONCLUSIVE
          ↓
       ChessDB
       ├─ ACCEPT → choose HCM and stop
       ├─ REJECT → next HCM
       └─ INCONCLUSIVE
                ↓
          Local Stockfish
          ├─ ACCEPT → choose HCM and stop
          └─ REJECT → next HCM
```

`Known:` Lichess acceptance is sufficient.

If Lichess verifies the HCM within the allowed threshold:

> accept immediately.

Do not ask ChessDB or local Stockfish for extra confirmation.

`Known:` Lichess rejection is also sufficient.

If Lichess clearly shows that the HCM is outside the allowed threshold:

> reject that HCM and move to the next one.

ChessDB does not get to overrule a clear Lichess rejection.

`Known:` ChessDB is used only when Lichess cannot decide or Lichess is unavailable.

If ChessDB verifies the HCM:

> accept immediately.

If ChessDB clearly rejects it:

> move to the next HCM.

`Known:` Local Stockfish is used only when the earlier sources cannot decide or are unavailable.

If local Stockfish verifies the HCM within the looser local threshold:

> accept immediately.

Do not inspect lower-ranked HCMs.

## HCM absent from an API list

`Known:` If the current HCM is absent from Lichess's returned move list, look at the actual last move Lichess returned.

If that last returned move is already outside the threshold:

> REJECT the HCM.

The missing HCM must be at least as bad or worse.

If the last returned move is still inside the threshold:

> Lichess is INCONCLUSIVE.

Continue to ChessDB.

The same rule applies to ChessDB.

For example:

```text
Lichess
candidate absent
last returned move within threshold
→ INCONCLUSIVE
→ ChessDB

ChessDB
candidate absent
last returned move within threshold
→ INCONCLUSIVE
→ Local Stockfish
```

## Waterfall repeats for every HCM

`Known:` Every HCM gets its own complete waterfall.

For example:

```text
HCM #1
→ Lichess
→ ChessDB
→ Local Stockfish
→ REJECT

HCM #2
→ start again from Lichess
```

However, API data and source state belong to the **position**, so B4 does not make unnecessary new API requests.

## Reuse source state across HCMs

`Known:` If Lichess or ChessDB already supplied a successful snapshot for this position, later HCMs reuse it.

`Known:` If one of those sources already exhausted its retry cycle and failed for this position, later HCMs do not start another retry cycle.

For example:

```text
HCM #1
Lichess fails completely
→ ChessDB rejects HCM #1

HCM #2
→ skip Lichess
→ reuse ChessDB snapshot
```

So:

> **the waterfall is per HCM, but API state is per position**

## Local Stockfish verification

`Known:` Local Stockfish verification is candidate-specific.

When an HCM reaches the local stage, run the deep local evaluation needed to compare:

- Stockfish's best move;
    
- the current HCM.
    

Use the looser local threshold defined in [[B2]].

If the HCM is within that threshold:

> ACCEPT.

If not:

> REJECT and move to the next HCM.

`Known:` If local Stockfish cannot return a usable evaluation or move after its own retry/error handling, generation must stop with a hard error.

At that point the verification chain is exhausted.

A technical engine failure must never look like a chess rejection.

## Hard-coded first Black moves

`Known:` Black has two deliberate hard-coded first-move repertoire choices:

```text
1.e4 → 1...c6
1.d4 → 1...d5
```

The first aims for the Caro-Kann.

The second aims for a Queen's Gambit Declined structure.

These two moves do **not** go through the B1 → Lichess → ChessDB → local waterfall.

`Known:` Against every other first White move, use the normal HCM/engine-verification process.

## Gemini

`Known:` Gemini should be removed from the Black-move algorithm completely.

It should not select:

- first moves;
    
- fallback moves;
    
- ordinary repertoire responses.
    

## Empty B1 shortlist

`Known:` If [[B1]] produces no HCMs at all, there is nothing to verify.

Skip the HCM loop and immediately run the final deep local Stockfish search:

```text
B1 shortlist empty
→ Local Deep Stockfish
→ choose top move
```

Save its source as:

`"Local Deep Stockfish"`

The selected move may have no human-game support. That is intentional.

## All HCMs rejected

`Known:` If every HCM is rejected in an ordinary position:

```text
all HCMs rejected
→ Local Deep Stockfish
→ choose its top move
```

Log clearly that no human candidate survived.

For example:

```text
[ENGINE FALLBACK]
All human candidates rejected
Using top deep-engine move: ...Nf6
Evaluation: -0.34
Source: Local Deep Stockfish
```

In the explicit Lichess mate case defined in [[B3]], the mate rule takes precedence:

```text
all HCMs rejected
→ use first Lichess move among the shortest mates
```

## SAN/LAN conversion

`Known:` If SAN/LAN conversion fails for an HCM, generation must stop with a hard error.

The candidate comes from the project's own chess data.

A conversion failure therefore means the programme's internal data or assumptions are inconsistent.

It is not a valid reason to reject the chess move and continue.

## Deep-verification state

`#roadmap` Add a `deepVerified` flag to the selected Black repertoire move.

Set:

`deepVerified = true`

when that exact selected move has already been verified with the deep local Stockfish process.

This includes:

- an HCM that passed deep local verification;
    
- the final `"Local Deep Stockfish"` fallback move.
    

Ordinary Lichess- or ChessDB-only selections begin with:

`deepVerified = false`

The later post-generation polishing pass should skip a selected response when:

`deepVerified = true`

If the selected Black response is later replaced, the new move starts with:

`deepVerified = false`

because verification belongs to the exact move that was checked, not permanently to the position.

## Bugs

`#bug` The current first-move hard-coded path can associate the general `bestCp` value with `...c6` or `...d5` even when that score belongs to another engine move. A saved move evaluation must belong to the move itself. The hard-coded repertoire choice does not remove the requirement that its displayed/stored evaluation be valid for that exact move.

## Roadmap

`#roadmap` Add detailed ACCEPT / REJECT / INCONCLUSIVE logging for every HCM, using the format established in [[B2]].

For example:

```text
[LICHESS]
Candidate: ...e6
Best: ...Nf6
Candidate eval: +0.02
Best eval: -0.10
Loss: 12 cp
Limit: 80 cp
ACCEPT
```

`#roadmap` Use `deepVerified` to prevent the later deep Stockfish polishing pass from repeating expensive verification that has already been completed for the same selected move.

## Notes

`Known:` B1 determines the human ranking. B4 never re-ranks it.

`Known:` The first HCM that passes any valid verification layer wins.

`Known:` An API source accepting a move is enough; local Stockfish is not an additional confirmation step.

`Known:` A clear API rejection is final for that HCM.

`Known:` Only an inconclusive result proceeds further down the waterfall.

`Known:` Hard-coded `...c6` against `1.e4` and `...d5` against `1.d4` are deliberate repertoire choices, not bugs.

`Known:` A final deep-engine fallback is allowed to choose a move that never appeared in the human data.
