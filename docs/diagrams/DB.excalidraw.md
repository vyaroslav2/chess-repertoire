## Text Elements
Deleting one row from
PositionCache deletes every
RepertoireNode built on that
position, and with them their
moves and study stats. The cache
is the parent of the repertoire,
not the other way round. ^I7to8akF

One row per position, move and
source: lichess, chessdb or
local_deep.

B3 writes local_deep. B2 sees
local_deep when checking whether
any engine cache exists, but
rebuilds engine lists only from
lichess or chessdb. Therefore a
local_deep-only row can block a
fresh API fetch while its score
is not used. ^LwHsSPGz

One row per position, database
type and move.

When a database has nothing for
a position, a marker row is
stored with the move name
_EMPTY_ and zero games, so the
app can tell "nothing there"
from "never asked". Marker rows
are filtered out on reading. ^jscqg6ZW

PGN is unique per repertoire, and
in practice each node has one
move history.

After a White move the generator
tries to reuse an existing node
by FEN, so that transpositions
merge into one node. That lookup
compares a full FEN against the
shortened FENs stored here, so it
never matches: the merge branch
never runs and a new node is
always created.

The FEN stored here is the
shortened one from FN. ^jas9QTAW

One move per from-node and SAN.

The Lichess and ChessDB scores
are divided by 100 before being
stored here, so they are in
pawns - while the same numbers
in EngineEvalCache are kept in
centipawns. ^t8riERvP

One row per repertoire and node:
each node can have one study card.
That card points to one target
move.

Explanation is not written by
Gemini: it is a generated one-line
summary of score, weighted volume
and evaluation.

Tags is never written or read by
anything. ^i2vdo63h
