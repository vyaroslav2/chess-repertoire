Called in six places: the position
cache, saving human moves (FC),
reading human moves (F), saving engine
scores (EC), creating a node, and once
at the start of scoring a Black move -
that one result is reused through B1
to B4.

Two test scripts call it as well.
Nothing else in the app builds
database keys. ^YNwXqWiF

Why: the same position reached
by different move orders, or after
a different number of moves, gets
the same key. Without this, every
cache lookup would miss and the
app would re-fetch everything. ^iA1rT7ub

Node FENs are stored shortened, so
anything reading one back gets a FEN
with only four parts. chess.js accepts
that and fills the two missing numbers
in as 0 and 1, so reading is safe.

Comparing is not. The generator looks
for an existing node by full FEN
against these shortened ones, so that
check never matches - see the note on
DB.06. ^3OZFUSwF

The local engine is also given the
shortened FEN, so it has no
half-move clock. It cannot know
how close the position is to the
fifty-move draw rule. Harmless in
the opening, wrong later on. ^yLzi5Xfl

No check that the FEN had four
parts to begin with. A malformed
FEN produces a short key and is
stored under it without complaint. ^QyTwPVYX
