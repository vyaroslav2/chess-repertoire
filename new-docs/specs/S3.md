# Step 3: Main Queue Loop

S3.01 Check whether the user has asked to stop — [[sigint|`SIGINT`]] ([[S0]]). If the flag is set, throw `UserRequestedStopError` ([[S0|S0.04]]). This is the only place the flag is read ([[S0|S0.08]]).

S3.02 Is the queue empty?
* yes `-->` the run is over. Go to S3.10.
* no `-->` continue.

S3.03 Take the next item off the queue.[^1] Is it already in `visitedList`?[^2]
* yes `-->` skip it and continue to the next queue item.
* no `-->` add it to the in-run `visitedList` and process.[^3] Marking happens here, at dequeue, not after processing.[^4]

S3.07 Hand off to [[HM]].

S3.08 Control comes back here when the position has been dealt with: [[HM]] filters White's moves, [[EW]] picks Black's reply, and [[RE.excalidraw|RE]] either ends the route or pushes the next position onto this queue ([[RE.excalidraw|RE.09]]). Then return to S3.01.

S3.09 Push order. The queue is LIFO, so the last position pushed is the first one taken. To read a log that runs from White's most popular move down to its least, the kept moves must therefore be pushed in the opposite order — least popular first. Pushing them in `siblingIndex` order ([[HM|HM.05]]) produces exactly the reverse of what is wanted.[^5]

## End of run

S3.10 Print the summary ([[TGL]]).[^6]

S3.11 Probability balances: endings + `rareDroppedTotal` + `tinyDroppedTotal` come to 100%, within the 0.0001% tolerance ([[TR.excalidraw|TR.41]]).

S3.12 Every Black response has `deepVerified` set to true ([[DB|DB.14]]).

S3.13 Every node carries opening metadata, either `PRESENT` or `VALID_ABSENCE` ([[DB|DB.06]]).

S3.14 Every route that ends carries a `stopReason` ([[DB|DB.20]]).

S3.15 All four pass `-->` the run closes as `[FINISHED]`. Any one fails `-->` hard error, and the run closes as `[FAILED]` ([[S0|S0.05]]).[^7]

[^1]: #note LIFO (last-in first-out) is decided for this generator architecture. LIFO leads to a depth-first approach, where we expand the first line to full depth before moving to the next. FIFO leads to breadth-first: we go through every move-1 opponent ply and our replies before starting move 2.

[^2]: #question What is the dedupe key: the [[node]] or the position? A node is a unique route, so the same node can never be queued twice and the check would never fire. A position can be reached by several routes, but that is a transposition, which [[TR.excalidraw|TR]] already owns. As written, S3.03 does not say which, and the two readings do very different things.

[^3]: `visitedList` is the wrong name to reuse. [[TR.excalidraw|TR.31]] already has a `visitedList`, holding fromNode + toNode + target FEN + gain for cascade duplicate detection. This one holds processed queue items. Two different structures, one name. One of them should be renamed. #bug #question 

[^4]: At dequeue is the safe order: a position can be pushed again while it is being processed, and marking at the end would let that copy through. Marking at dequeue also means a position queued twice before either copy is reached is only ever processed once.

[^5]: #question This was never written down anywhere. [[EW|EW.12]] says children are pushed "in order in which the resulting generation will produce nodes in descending popularity order", which does not say which order that is. Now that [[RE.excalidraw|RE.09]] pushes one position at a time, there is no batch left to order, so the decision belongs to whichever block walks the kept moves — probably [[HM|HM.06]].

[^6]: #question What is in the summary? [[TGL]] defines nothing yet, and it says to write only what other notes cite. This cites it, so it now owes a definition. [[TR.excalidraw|TR.19]] already names cascade counts — revisits, refires, duplicates, tinyDropped, repetitions — which look like summary material.

[^7]: #question Who actually writes the tag? [[S0|S0.05]] says the outermost try/catch decides, from the type of error thrown. S3.02 used to say the tag is set here, on these conditions. Both cannot own it. Treating a failed check as a thrown error keeps [[S0]] the only writer, which is why it is written that way above — worth confirming.
