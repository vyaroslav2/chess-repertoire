# SCR — Общий кэш (перевод SC)

SCR — перевод [[SC]] на русский. Номера пунктов те же: SCR.11 = SC.11. Если тексты расходятся, верен [[SC]].

SC позволяет двум людям (пользователю и его другу) строить деревья каждому на своём ПК и делить один кэш оценок Stockfish. Позицию, которую уже посчитал один, другому считать не нужно. Это работает, только если оба запускают одинаковый поиск и хранят одинаковые поля. Черновик, 2026-11-07. Пока ничего не сделано.

## Зачем

SCR.01 **Поиск медленный.** Один поиск на 200M узлов занимает около 8 минут на ПК пользователя (медиана по 165 поискам, октябрь 2026; самый быстрый — 6,7 мин). Каждой новой позиции нужен один такой поиск. Два человека, которые строят деревья по одним и тем же дебютам, считают много одних и тех же позиций.

SCR.02 **Кэш уже устроен под это.** Оценка хранится по точному `fullFen` и настройкам движка ([[DB|DB.32]]). Два кэша, собранные с одними настройками, хранят оценки одного вида, поэтому их можно слить.

SCR.04 **Совпадать должен файл, а не база данных.** Проекты могут различаться. Каждая сторона хранит оценки в своих таблицах, под своими именами, с любыми дополнительными столбцами. Общими должны быть настройки движка (SCR.10), поля каждой оценки (SCR.21) и файл обмена (SCR.50).

SCR.03 **Одни настройки должны давать один результат.** С одним потоком Stockfish детерминирован: та же версия, та же позиция и те же настройки дают тот же ход, оценку, глубину и число узлов на любом процессоре. С несколькими потоками результат меняется от запуска к запуску, поэтому делиться им небезопасно.

## Настройки движка

SCR.10 **Оба используют ровно эти настройки.** Это нынешние настройки EW.09 ([[EW|EW.09]], [[generation-config]]):
* Stockfish 19, официальный релиз, в `bin/stockfish.exe`.
* Новый процесс Stockfish на каждый поиск, чтобы хэш начинался пустым.
* `setoption name Threads value 1`
* `setoption name Hash value 1024`
* `setoption name MultiPV value 1`
* Все остальные опции — по умолчанию. В частности, без `SyzygyPath`: таблицы эндшпиля меняют результат.
* `position fen <fullFen>`, затем `go nodes 200000000`.

SCR.11 **Как читать результат** — правило EW.09 без изменений:
* Отбросить ту одну строку, у которой `nodes` не меньше 200000000. Она относится к глубине, которую оборвал лимит узлов.
* Пропустить граничные строки (`lowerbound`, `upperbound`).
* Взять самую большую из оставшихся глубин и её последнюю точную строку. Первый ход в ней — лучший ход; её оценка — оценка позиции.
* `bestmove` не учитывать.
* Пример: d24 заканчивается на 150M; d25 ещё идёт на 200M. Строка d25 отбрасывается, записывается последняя точная строка d24, с `depth` 24.


SCR.12 **Сначала проверить сборку.** Оба первым делом запускают `stockfish.exe bench`. Число `Nodes searched` должно совпасть. На ПК пользователя оно равно **2497913**. Другое число значит другой движок: остановиться и выяснить причину.

## Что хранится

SCR.20 **Два новых столбца в `EngineCacheEvaluation`**, оба из строки, которую оставляет SCR.11:
* `nodes`: число узлов из этой строки. С одним потоком оно точное, поэтому это самая строгая проверка того, что два движка совпадают (SCR.03).
* `pv`: вся линия, ходы UCI через один пробел. Видно, какой ответ ожидает Stockfish.

SCR.21 **Общие поля.** Каждая сторона должна хранить их для каждой оценки, в любых таблицах и столбцах:
* `fullFen`: все шесть полей, в каноническом виде (одиночные пробелы, счётчики на месте).
* `uci`: лучший ход.
* `san`: тот же ход в SAN.
* `cp` или `mate`: задано ровно одно из них. С точки зрения белых ([[DB|DB.15]]): когда ход чёрных, знак Stockfish меняется. `mate` никогда не равен 0.
* `depth`, `nodes`, `pv` (SCR.11, SCR.20).
* Настройки, с которыми посчитана оценка (SCR.10), в любом виде: в этом проекте — хэш профиля (SCR.22).

Сторона может хранить больше (здесь: `id`, `rank`, `fetchedAt`). Лишние поля никогда не экспортируются, а при импорте получают свои значения по умолчанию. Хранить меньше нельзя: отброшенное поле не передать дальше.

SCR.24 **`rank` не входит в общие поля** (решено 2026-11-07). С MultiPV 1 (SCR.10) у поиска одна линия, поэтому каждая общая оценка имеет ранг 1, и поле ничего не сообщает. Этот проект оставляет свой столбец `rank` как есть ([[DB|DB.32]]): 1 для лучшего хода EW.09, `null` для оценки селектора. При импорте добавленная оценка получает `rank` 1 (SCR.52). Для рангов 2 и выше нужен MultiPV 3, а это другой поиск: его ранг 1 не совпадает с базовым MultiPV 1, поэтому ему нужны новые настройки и свой кэш.

SCR.22 **Профиль этого проекта.** Здесь настройки хранятся как хэш sha256, `engineProfile` ([[DB|DB.32]]). В него добавляется одно поле, `record: 2`, что значит «оценка также содержит `nodes` и `pv`». Поэтому хэш меняется, и ни одну строку, записанную до SC, нельзя прочесть так, будто в ней есть эти поля. Хэш — собственный ключ этого проекта: он никогда не попадает в файл обмена, и проекту друга вычислять его не нужно. Сделано 2026-11-07: теперь хэш равен `6af3998c38326a319fa5ba8e5d820ef274585b83660559e264d1f1dd9752ebaf` (был `da64ab3e…`).


SCR.23 **Время в кэше не хранится.** Оно зависит от ПК, поэтому у двух людей никогда не совпадает. Оно пишется в журнал поисков (SCR.30).

## Журнал поисков

SCR.30 **Новый файл `new-docs/logs/engine-searches.jsonl`.** Одна строка на каждый настоящий поиск; попадание в кэш ничего не пишет. Код только дописывает в него: файл никогда не стирается, в отличие от `tree-events.jsonl`, который стирается в начале каждого запуска. Как и весь `logs/`, он не коммитится.

SCR.31 **Каждая строка содержит:** `at` (когда закончился поиск), `kind` (`deep` или `selector`), `fullFen`, `uci` (только для селектора: ход, который считали), `engineProfile`, `seconds` (от запуска Stockfish до его выхода), `depth`, `nodes`.

SCR.32 **Среднее время.** Скрипт читает файл и выводит для текущего глубокого профиля: число поисков, медиану и среднее время. Для планирования брать медиану: если ПК уходит в сон во время поиска, среднее завышается.

## Чистый старт

SCR.40 **Старый кэш и старое время стираются при следующей генерации, не раньше.** Пользователь решил так 2026-11-07. Перед этим запуском:
* Удалить все строки `EngineCache` в `dev.db` (а каскадом — все `EngineCacheEvaluation`). Это охватывает все три старых профиля: глубокие оценки на 200M (у большинства нет `depth`), глубокие оценки на 2M от 3 ноября и оценки селектора.
* `engine-searches.jsonl` начинается пустым.
* Одноразовый скрипт делает и то, и другое. Пользователь запускает его прямо перед следующей генерацией. Скрипт никогда не трогает `test.db` и таблицы вне кэша движка.

SCR.41 После этого запуска у каждой оценки в кэше есть `depth`, `nodes` и `pv`, а у каждого поиска — время.

## Обмен

SCR.50 **Файл обмена** — JSON в UTF-8. Настройки записаны в простом виде один раз в начале, чтобы любой проект мог их проверить, не зная, как их хранит другой:

```json
{
  "format": "shared-eval-cache",
  "formatVersion": 1,
  "settings": {
    "engine": "Stockfish 19",
    "bench": 2497913,
    "nodes": 200000000,
    "threads": 1,
    "hashMb": 1024,
    "multiPv": 1,
    "record": 2
  },
  "evals": [
    {
      "fullFen": "rnbqkbnr/pppppppp/8/8/4P3/8/PPPP1PPP/RNBQKBNR b KQkq - 0 1",
      "uci": "c7c6",
      "san": "c6",
      "cp": 30,
      "mate": null,
      "depth": 24,
      "nodes": 187654321,
      "pv": "c7c6 d2d4 d7d5"
    }
  ]
}
```

(Оценка выше выдумана, чтобы показать формат.) `cp` и `mate` присутствуют оба: одно — число, другое — `null`. Других полей нет. Оценки отсортированы по `fullFen`, поэтому два экспорта одного кэша совпадают байт в байт.

SCR.51 **Экспорт.** Скрипт пишет в файл каждую оценку, посчитанную с настройками SCR.10. Здесь: каждую строку текущего глубокого профиля (SCR.22).

SCR.52 **Импорт.** Скрипт читает файл другого человека:
* `format`, `formatVersion` и каждое поле `settings` должны совпадать со своими. При любом различии отвергается весь файл, с указанием поля.
* Оценки сопоставляются по `fullFen`. Позиция, которой ещё нет в кэше, добавляется под собственным ключом этой стороны (здесь: профиль SCR.22, новые id, `rank` = 1, `fetchedAt` = сейчас).
* Позиция, которая уже есть в кэше, служит проверкой: `uci`, `san`, `cp`, `mate`, `depth`, `nodes` и `pv` должны совпасть. Совпали — пропустить. Любое различие — жёсткая ошибка с указанием позиции и различающихся полей, и из этого файла ничего не записывается. Два движка, которые расходятся, смешивать нельзя.

## Проверка

SCR.60 **Прежде чем чем-то делиться:**
1. Оба запускают `bench` (SCR.12).
2. Оба используют настройки SCR.10 и хранят поля SCR.21.
3. Выбрать 10 позиций, которых нет в кэше ни у кого. Оба их считают.
4. Один экспортирует, другой импортирует. Импорт проверяет настройки, затем сравнивает каждое поле (SCR.52). Все 10 должны совпасть.

## Вне рамок

SCR.70 **Оценками селектора не делятся.** Они создаются, только когда включён `humanEvidence`, а он выключен. У них другой профиль и другое правило чтения (они оставляют строку остановки, [[HEG|HEG.21]]). Если ими будут делиться позже, им нужны свой экспорт и своя проверка.
