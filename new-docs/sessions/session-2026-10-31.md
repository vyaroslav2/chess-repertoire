## Done
- `npm run tree-log` prints a run as a log ([[TGL]]), step by step in the generator's own order ([[S3]]): `[Queue]`, `Dequeue 1. e4 c6, waiting 1`, White's moves as fetched, then one numbered step per White move. Least common first, as the code handles them, so the most common comes off the queue next. It writes `new-docs/logs/tree-log.md`.
- A step shows the route and cumProb, the FEN, the baseline (eval, depth, time), the selector's table, the reply, the budget if a switch spent any, the queue push or the ending, and the elapsed time. A `----` rule above each step, `====` above each position.
- The selector's table has the champion on top. The verdict says `champion`, or `pass` on a move that passes, and is blank on a dropped move. The other columns show why it was dropped: no 2M eval, safe gain too low, or 200M loss too high. The header shows a limit only when the line budget has dropped below the cp limit, e.g. `200M loss ≤20`.
- The config block holds the selector's limits: `safe gain >1.0`, `200M loss ≤30`, `line budget 50`. `[Summary]` sits above the steps and counts the whole tree. A finished run has no `Waiting` line; a stopped one shows `Waiting 6: the run stopped early`.
- Too-rare moves are marked in White's list, with the cumProb the threshold checks (`too rare: cumProb 0.06%`), and get no step. Transpositions print their owner and cascade. Sweeps get a block.
- A node shows its route's share when a cascade changed its cumProb: `cumProb 3.50% (route 0.78%)`. This answers why a child can show more than its parent.
- The generator records each run to `new-docs/logs/tree-events.jsonl` (`src/lib/core/run-events.ts`): its config, search times, cache hits, the queue, cascades and sweeps. This changes no tree logic. The log prints from these events. A tree with no matching events is replayed, and those facts show as dashes. A test confirms the replay gives the recorded order.
- `npm run tree-log -- --route "e4 c6 d4"` or `-- --step 12` prints one part. `npm run tree-log:mock` prints a made-up finished run with every block, to `new-docs/logs/tree-log-mock.md`.
- `explorerRatings` is now 1600, 1800 (1600–1999), in `config.ts` and [[generation-config]]. The Explorer cache key changed, so the next generation fetches every position again. Not committed.
- The 248 nodes with cumProb 0 in `dev.db` are by design: 240 too rare and 8 transpositions. The old run's higher `minCumProb` is why 1.c4, 1.b3 and 1.Nc3 are among them.
- All 248 tests pass on `test.db`, before the last two log changes. After those, the log's tests pass, and the typecheck is clean.

## Decisions
- The log is printed after a run, not from inside the generator, so a rerun takes seconds. What the database doesn't hold comes from the events. The console log and `treegen-*.md` stay as they were.
- The log follows the code's order, not the most-common-first order: the queue is last in, first out, so printing e4 first would show the queue wrongly.
- For now, the log starts from move 2 and prints only the lines under `1. e4 c6` and `1. d4 d5`. The generator is unchanged, so a new generation still replies to the other first moves, and the summary counts them.
- The selector still skips Black's first move. HES.10's reason is that the move is fixed, which covers only 1. e4 and 1. d4; the check in the code also skips the other 10 first moves. Left as it is for now.
- Explorer's 12 moves per position are enough: the cap stays.
- `[Summary]` goes first: a full log will be long, and the outcome should be seen without scrolling.
- Cut from the log as redundant: `Selector d5 stays` and `d5 replaces g6`, `Selector not run: ...`, the switches' share of judged cumProb, `Waiting 0`, `next first`, and "on Black's move" in `Ends`. The generator's own summary keeps its share (HEG.41). A depth cap can only be reached on Black's move.
- Words: `Baseline`, not `Stockfish`; `#1` for a step, as `1.` would read as a chess move. Safe gain is in points.
